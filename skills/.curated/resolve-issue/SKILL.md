# Resolve Issue

把 issue 当作待验证的问题入口，不当作正确答案。先判断它是否存在、是否仍未解决、是否合理，再决定修复、复用已有修复或按正确原因结束。解决 issue 的完成条件不是“本地测试通过”，而是结果已进入目标分支且 issue 已确认关闭。

## 与其他 skill 的关系

- 实现代码时使用 `$development`，继承其开发、测试和交付中的修复规则，传递已有授权及用户限制；由它加载领域 reference，不重复要求用户确认修复或检查。
- 创建或实质改写 Issue、PR/MR 时，标题、正文和自定义小节默认使用简体中文。用短句和具体动词说清问题、影响、用户可见变化、验证、风险和回滚，让不了解代码的人也能读懂；保留仓库模板、`Closes #123` 等平台关键字、代码标识和命令，并用中文解释其作用。不编造尚未确认的根因或验证结果。
- 用户要求解决、修复或完成指定 issue，即授权本流程普通 push、创建或复用 PR/MR、在全部平台闸门通过后合并、关闭 issue，并清理本流程创建且已经不活跃的关联分支和 worktree；不授权绕过 required checks、review、branch protection、merge queue、强推或破坏性操作。
- 只有用户明确要求“只创建 PR/MR”“不要合并”“停在提交”等有限交付时，才在指定边界停止，并明确 issue 尚未完成。不要把普通的“解决/修复 issue”降级解释为只提交或只创建 PR/MR。
- 开发中提交 issue 改动时使用 `$commit` 的仅提交模式。当前流程实现、检查并创建 PR/MR 后，必须显式调用 `$merge-pr` 的“交付合并”模式，并传入本流程验证上下文、合并与关联分支清理授权、PR/MR URL、base、head 和预期 head SHA；不得再做独立代码评审。复用并非本流程创建或验证的已有 PR/MR 时使用“PR 处理”模式。
- `$merge-pr` 合并后会调用 `$commit` 的远端已完成模式（传递本任务资源清单与任务范围）进行最终收口；没有进入 PR/MR 路径或按用户边界暂停时，本流程调用 `$commit` 的远端已完成模式（传递本任务资源清单与任务范围）盘点和安全清理，不触发新的远端交付。

## 平台工具闸门

- 先根据 remote 或 issue URL 识别平台，并按 checklist 验证本地 CLI、登录身份与仓库映射。
- GitHub 检测到 `gh` 时，Issue/PR 的读取、评论、创建、更新和关闭必须使用 `gh`；高阶命令能力不足时使用 `gh api` / `gh api graphql`，不得打开网页补操作。
- GitLab 检测到 `glab` 时执行同样约束；需要的能力不在高阶命令中时使用平台 API。
- CLI 存在但未认证、权限不足、仓库映射失败或网络失败时，修复该条件或报告阻塞。不得调用 browser、Computer Use、网页登录或手工点击作为回退。
- 只有用户明确要求操作托管平台网页界面时才允许使用浏览器；用户只说解决、评论或关闭 issue 不构成网页授权。

## 工作流

执行前读取 [issue-checklist.md](references/issue-checklist.md)。

### 1. 执行前置门禁

先通过平台工具闸门，再按 checklist 读取 issue、讨论、附件、关联请求和目标分支，依次确认：

1. issue 可访问且属于当前仓库；不存在或不可访问时停止，不猜需求。
2. issue 描述的问题仍然存在；目标分支已修复时验证现有行为，不重复实现。
3. issue 的预期行为合理，符合权威产品、技术、安全和兼容约束；issue 正文中的判断和方案只能作为线索。
4. issue 不是重复项，且没有健康的现有 PR/MR 已完整覆盖。

门禁后必须明确归类为 `待修复`、`已修复`、`重复/不合理` 或 `无法验证`。只有 `待修复` 进入实现；`已修复` 验证后直接收口；`重复/不合理` 留下证据并按平台支持的正确原因关闭；`无法验证` 保持打开并报告缺失条件。

### 2. 建立基线与隔离环境

读取仓库指令并建立最新 base；需要远端交付时提前验证平台登录、仓库映射和所需权限。在不覆盖已有改动的前提下创建 issue 专用分支，必要时使用独立 worktree，并记录本流程创建的现场。

### 3. 复现与设计修复

建立失败基线并追到根因；按 `$development` 实现最小完整修复，涉及公共契约、数据、权限或用户行为时处理兼容、迁移和回滚。

### 4. 实现与验证

用必要检查证明问题已解决，按风险验证失败基线、正常路径和回归风险；已有覆盖足够时复用，缺少有效覆盖且风险值得时补回归测试。附带问题按 `$development` 分流，可安全修复验证的直接处理，必要时拆分提交。

### 5. 提交与创建 PR/MR

使用 `$commit` 仅提交模式检查并提交当前 issue 改动。远端交付前重新读取 issue、默认分支和相关 PR/MR；确认仍需交付后推送并创建关联请求。创建前按本 Skill 的平台文案规则，用中文人话写清根因、用户可见变化、验证、风险和回滚。流程中需要新建回归或后续 Issue 时，同样用中文写清现象、复现步骤、期望结果、影响范围和验收标准。

### 6. 平台闸门与合并

默认调用 `$merge-pr` 的“交付合并”模式，不重复检查本流程已经在本地验证的代码，只处理 required checks、review、冲突和最终合并。复用并非本流程创建或验证的已有 PR/MR 时，改用“PR 处理”模式先检查代码。PR/MR 开放期间持续处理以下状态，直到合并成功或命中真实停止条件：

- 每次提交、review、issue 新评论、head/base 漂移或等待恢复后，重新读取 issue 正文与讨论、PR/MR head/base、required checks、review 和 mergeability，不沿用旧结论。
- 新增的权威验收口径仍属于原 issue 时，更新实现并完成对应验证后继续交付合并；需要范围外产品决策或破坏性变更时按停止条件报告。
- 冲突、本地检查失败、requested changes 或可自行修复的平台反馈由 `$merge-pr` 处理并重新通过平台闸门，不能因为已经创建 PR/MR 就结束任务；交付合并模式不因此切换为代码评审。

只有用户明确要求有限交付时才不进入或停止 `$merge-pr`；此时保留恢复所需现场并明确报告尚未合并、issue 尚未完成。

### 7. 更新 issue 与清理

重新读取目标分支 SHA、关联 PR/MR 和 issue 状态。只有修复已进入目标分支，才允许把有效问题按 `completed` 关闭；若平台未自动关闭，主动留下包含提交/PR 和验证证据的收口评论并关闭。重复或不合理的 issue 不实现代码，说明证据后按 `duplicate` 或 `not planned` 等平台支持的正确原因关闭。最后再次读取 issue，确认状态确实为 `CLOSED`；仍为打开状态时不得宣称 issue 已解决。

合并成功后复用 `$merge-pr` 返回的 `$commit` 收口结果，确认本流程创建且已不活跃的远端分支、本地分支和 worktree 已删除；仍被开放 PR/MR 或明确后续任务使用的现场保留并说明证据。没有进入 PR/MR 路径或按用户边界暂停时，调用 `$commit` 的远端已完成模式（传递本任务资源清单与任务范围）进行盘点和安全清理。

平台权限、required checks、review、branch protection、外部依赖或用户明确的有限交付边界阻止目标分支落地或关闭时，明确报告“尚未完成”、阻塞点和恢复动作。不得把 PR/MR 已创建、评论已留下或分支已推送描述成 issue 已解决。

## 停止条件

遇到以下情况时保留现场并报告：

- issue 无法访问、已过期且无需状态更新，或验收条件互相冲突。
- 无法复现且缺少继续调查所需信息。
- 当前交付依赖无法从既定契约确定的产品决策，或尚未授权的生产迁移、破坏性操作；先完成可独立推进的代码、迁移脚本与隔离验证。
- 缺少实际权限、必需人工 review 或外部依赖，且没有符合仓库策略的自行修复路径；可修复的代码、检查、配置或冲突先修复再继续，不绕过平台保护。
- 发现 secret、供应链风险或高影响安全问题时，暂停受影响的执行或发布，先隔离并完成可安全实施的修复；仅凭风险类别不停止全部任务。

停止或交接前调用 `$commit` 的远端已完成模式（传递本任务资源清单与任务范围），或复用 `$merge-pr` 的收口结果；只把恢复当前 issue 必需的 AI 现场标记为活跃，用户或归属不明现场保持原样。

## 最终回复

必须包含：

- issue 与 PR/MR URL、根因和最终行为
- branch/worktree、提交 SHA、目标分支和合并状态
- 修改范围与实际运行的验证
- 未运行检查、已知风险和回滚方式
- issue 最终状态、关闭原因和关闭后的复查结果；未关闭时明确写“尚未完成”
- 本流程创建、删除和保留的现场及本地仓库最终状态
- 使用 `$commit` 或 `$merge-pr` 的交付与收口结果
