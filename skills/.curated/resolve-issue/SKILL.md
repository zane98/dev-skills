# Resolve Issue

把 issue 当作待验证的问题入口，不当作正确答案。先判断它是否存在、是否仍未解决、是否合理，再决定修复、复用已有修复或按正确原因结束。解决 issue 的完成条件不是“本地测试通过”，而是结果已进入目标分支且 issue 已确认关闭。

## 与其他 skill 的关系

- 实现代码时使用 `$development`，由它按改动范围加载前端、后端和语言 reference，并遵循仓库自己的指令。
- 用户要求解决、修复或完成指定 issue，即授权本流程普通 push、创建或复用 PR/MR、在全部平台闸门通过后合并、关闭 issue，并清理本流程创建且已经不活跃的关联分支和 worktree；不授权绕过 CI、review、branch protection、merge queue、强推或破坏性操作。
- 只有用户明确要求“只创建 PR/MR”“不要合并”“停在提交”等有限交付时，才在指定边界停止，并明确 issue 尚未完成。不要把普通的“解决/修复 issue”降级解释为只提交或只创建 PR/MR。
- 开发中提交 issue 改动时使用 `$commit` 的仅提交模式。创建或复用 PR/MR 后必须显式调用 `$merge-pr`，并把本流程的合并与关联分支清理授权、PR/MR URL、base、head 和预期 head SHA 传入。
- `$merge-pr` 合并后会调用 `$commit` 的远端已完成模式进行最终收口；没有进入 PR/MR 路径或按用户边界暂停时，本流程调用 `$commit` 的远端已完成模式盘点和安全清理，不触发新的远端交付。

## 工作流

执行前读取 [issue-checklist.md](references/issue-checklist.md)。

### 1. 执行前置门禁

按 checklist 读取 issue、讨论、附件、关联请求和目标分支，依次确认：

1. issue 可访问且属于当前仓库；不存在或不可访问时停止，不猜需求。
2. issue 描述的问题仍然存在；目标分支已修复时验证现有行为，不重复实现。
3. issue 的预期行为合理，符合权威产品、技术、安全和兼容约束；issue 正文中的判断和方案只能作为线索。
4. issue 不是重复项，且没有健康的现有 PR/MR 已完整覆盖。

门禁后必须明确归类为 `待修复`、`已修复`、`重复/不合理` 或 `无法验证`。只有 `待修复` 进入实现；`已修复` 验证后直接收口；`重复/不合理` 留下证据并按平台支持的正确原因关闭；`无法验证` 保持打开并报告缺失条件。

### 2. 建立基线与隔离环境

读取仓库指令并建立最新 base；需要远端交付时提前验证平台登录、仓库映射和所需权限。在不覆盖已有改动的前提下创建 issue 专用分支，必要时使用独立 worktree，并记录本流程创建的现场。

### 3. 复现与设计修复

建立失败基线并追到根因；按 `$development` 实现最小完整修复，涉及公共契约、数据、权限或用户行为时处理兼容、迁移和回滚。

### 4. 实现与验证

补充能证明问题已解决的测试并按风险验证失败基线、正常路径和回归风险；独立问题只记录，不夹带修复。

### 5. 提交与创建 PR/MR

使用 `$commit` 仅提交模式检查并提交当前 issue 改动。远端交付前重新读取 issue、默认分支和相关 PR/MR；确认仍需交付后推送并创建关联请求，正文按 checklist 记录根因、方案、验证、风险和回滚。

### 6. 评审与合并

默认调用 `$merge-pr`，按独立评审标准处理 CI、review、冲突和最终合并。PR/MR 开放期间持续处理以下状态，直到合并成功或命中真实停止条件：

- 每次提交、review、issue 新评论、CI 完成、head/base 漂移或等待恢复后，重新读取 issue 正文与讨论、PR/MR head/base、review、检查和 mergeability，不沿用旧结论。
- 新增的权威验收口径仍属于原 issue 时，更新实现与测试后重新进入评审；需要范围外产品决策或破坏性变更时按停止条件报告。
- 冲突、检查失败、requested changes 或可自行修复的评审意见由 `$merge-pr` 处理并重新通过全部闸门，不能因为已经创建 PR/MR 就结束任务。

只有用户明确要求有限交付时才不进入或停止 `$merge-pr`；此时保留恢复所需现场并明确报告尚未合并、issue 尚未完成。

### 7. 更新 issue 与清理

重新读取目标分支 SHA、关联 PR/MR 和 issue 状态。只有修复已进入目标分支，才允许把有效问题按 `completed` 关闭；若平台未自动关闭，主动留下包含提交/PR 和验证证据的收口评论并关闭。重复或不合理的 issue 不实现代码，说明证据后按 `duplicate` 或 `not planned` 等平台支持的正确原因关闭。最后再次读取 issue，确认状态确实为 `CLOSED`；仍为打开状态时不得宣称 issue 已解决。

合并成功后复用 `$merge-pr` 返回的 `$commit` 收口结果，确认本流程创建且已不活跃的远端分支、本地分支和 worktree 已删除；仍被开放 PR/MR 或明确后续任务使用的现场保留并说明证据。没有进入 PR/MR 路径或按用户边界暂停时，调用 `$commit` 的远端已完成模式进行盘点和安全清理。

平台权限、CI、review、外部依赖或用户明确的有限交付边界阻止目标分支落地或关闭时，明确报告“尚未完成”、阻塞点和恢复动作。不得把 PR/MR 已创建、评论已留下或分支已推送描述成 issue 已解决。

## 停止条件

遇到以下情况时保留现场并报告：

- issue 无法访问、已过期且无需状态更新，或验收条件互相冲突。
- 无法复现且缺少继续调查所需信息。
- 修复需要超出 issue 范围的产品决策、数据迁移或破坏性变更。
- CI、权限、required review 或外部依赖阻塞交付。
- 发现 secret、供应链风险或高影响安全问题。

停止或交接前调用 `$commit` 的远端已完成模式，或复用 `$merge-pr` 的收口结果；只把恢复当前 issue 必需的 AI 现场标记为活跃，用户或归属不明现场保持原样。

## 最终回复

必须包含：

- issue 与 PR/MR URL、根因和最终行为
- branch/worktree、提交 SHA、目标分支和合并状态
- 修改范围与实际运行的验证
- 未运行检查、已知风险和回滚方式
- issue 最终状态、关闭原因和关闭后的复查结果；未关闭时明确写“尚未完成”
- 本流程创建、删除和保留的现场及本地仓库最终状态
- 使用 `$commit` 或 `$merge-pr` 的交付与收口结果
