# Resolve Issue Checklist

## 1. Issue 信息

收集并核对：

- URL/编号、仓库、状态、作者、labels、assignee 和 milestone。
- 标题、正文、全部评论、附件、关联 issue/PR/MR 和提交。
- 实际行为、期望行为、复现步骤、环境和验收条件。
- 是否重复、是否已有开放修复、是否已在默认分支解决。

优先使用托管平台 CLI/API 获取结构化信息。读取 issue 后还要查看讨论；正文可能已经被后续决定修正。验收条件优先采用 maintainer/负责人明确确认的决定，其次是 issue 作者补充；普通参与者评论作为证据而不是自动要求。权威来源冲突时停止并澄清。

已有相关 PR/MR 时分流：

- 完整覆盖且健康：不创建重复请求，按授权评审/合并已有请求。
- 部分覆盖：列出缺口，决定协作补充或创建明确说明关系的替代请求。
- stale、失败或方向错误：记录证据后再决定替代，不默认修改别人或 fork 的分支。
- 默认分支已解决：停止实现，验证后更新 issue。

## 2. 开发前检查

- 读取仓库级和目录级开发指令。
- 确认默认远端、base 分支和分支命名规范，不硬编码 `origin/main`。
- 检查当前工作区、其他 worktree、已有同名分支和未完成任务。
- 记录 base SHA、issue 状态和已有相关 PR/MR。
- 用户要求远端交付时，提前验证托管平台登录态、仓库映射、push 和创建 PR/MR 的权限；合并权限仍由 `$merge-pr` 单独检查。
- 确定复现方法、风险面和最小验收集合。

## 3. 实现检查

- 失败基线能够说明问题真实存在。
- 修复针对根因，不扩大无关重构。
- 新测试在旧行为上失败、在新行为上通过，或说明无法这样验证的原因。
- API/schema/config/权限变化具有兼容和迁移策略。
- 日志不泄露敏感数据，错误路径可诊断。
- 文档、示例和产品说明只在真实行为发生变化时同步更新。

## 4. PR/MR 正文

建议结构：

```markdown
## 关联 Issue
- Closes #<id>

## 根因
- 说明问题为何发生，以及影响范围。

## 改动
- 说明关键实现和用户可见行为。

## 验证
- 列出实际运行的命令和结果。
- 说明未覆盖区域。

## 风险与回滚
- 说明兼容、部署或迁移风险。
- 给出回滚方式。
```

标题和语言遵循仓库已有规范，不强制中文。创建前复查 `base...HEAD` 的提交、文件和 diff，确保没有夹带其他任务。

## 5. 完成交付

- PR/MR 已独立评审，必需 CI/review 通过。
- 最终结果已进入目标分支，记录 merge/squash commit SHA。
- issue 已自动关闭或已留下准确状态更新。
- 未调用 `$merge-pr` 时，完成或暂停前调用 `$commit` 默认收口；已调用时复用其收口结果，不重复清理。
- 无法合并或关闭时把恢复本 issue 必需的 AI 现场标记为活跃并给出恢复条件；用户或归属不明现场保持原样并报告。

CI pending 时记录 PR/MR URL、精确 head SHA、pending checks、最后检查时间和恢复条件。只要求创建请求时可以在此交付；要求完整闭环时使用可用的等待/监控机制，恢复后重新读取全部远端状态，不能沿用旧的绿色检查或 review。
