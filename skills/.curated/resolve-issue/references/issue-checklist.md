# Resolve Issue Checklist

## 0. 托管平台 CLI 闸门

先根据 remote 或 issue URL 识别平台，再验证 CLI、登录态和仓库映射：

```bash
# GitHub
command -v gh
gh auth status
gh repo view --json nameWithOwner,defaultBranchRef

# GitLab
command -v glab
glab auth status
glab repo view
```

- GitHub 且 `gh` 可用时，Issue、PR、评论、关联关系和关闭状态一律使用 `gh` 读取或修改；高阶命令缺少能力时使用 `gh api` / `gh api graphql`。
- GitLab 且 `glab` 可用时执行同样约束；命令能力不足时使用平台 API。
- CLI 未安装、未认证、权限不足、仓库映射失败或网络失败时，修复该条件或报告阻塞，不得切换 browser、Computer Use、网页登录或手工点击。
- 只有用户明确要求操作托管平台网页界面时才允许浏览器。普通“解决 issue”“创建 PR”“合并”都不授权网页回退。

## 1. Issue 前置门禁

### 1.1 存在性

- 使用托管平台 CLI/API 读取 URL/编号，确认仓库映射、状态、作者、labels、assignee 和 milestone。
- 读取失败时区分不存在、无权限、网络失败和仓库不匹配；未确认前不进入实现。
- issue 已关闭时先核对关闭原因和当前目标分支；关闭结论仍有效则不重复实现，问题复发时按仓库惯例决定重开还是创建回归 issue。

### 1.2 是否仍未解决

- 标题、正文、全部评论、附件、关联 issue/PR/MR 和提交。
- 实际行为、期望行为、复现步骤、环境和验收条件。
- 是否重复、是否已有开放修复、是否已在默认分支解决。
- 在目标分支或权威运行环境验证当前行为；不能仅凭 issue 为 `OPEN` 推断问题仍存在。

### 1.3 合理性

- 对照仓库当前 PRD、技术约束、接口契约、安全边界、兼容要求和维护者决定，判断期望行为是否成立。
- 把 issue 的“初步判断”“建议方案”视为假设；先验证根因，再选择实现。
- 若诉求与权威事实冲突、会制造安全/数据风险或已被后续决定否决，判为不合理，不用代码迎合错误前提。

### 1.4 分流结论

| 结论 | 动作 |
| --- | --- |
| `待修复` | 建立失败基线并进入实现 |
| `已修复` | 验证目标分支行为，引用已有提交/PR，关闭为 completed |
| `重复/不合理` | 不实现；留下证据，关联主 issue 或权威决定，按 duplicate/not planned 等正确原因关闭 |
| `无法验证` | 保持打开；报告缺失权限、环境、证据或产品决定 |

优先使用托管平台 CLI/API 获取结构化信息。读取 issue 后还要查看讨论；正文可能已经被后续决定修正。验收条件优先采用 maintainer/负责人明确确认的决定，其次是 issue 作者补充；普通参与者评论作为证据而不是自动要求。权威来源冲突时停止并澄清。

已有相关 PR/MR 时分流：

- 完整覆盖且健康：不创建重复请求，按当前交付边界评审/合并已有请求。
- 部分覆盖：列出缺口，决定协作补充或创建明确说明关系的替代请求。
- stale、失败或方向错误：记录证据后再决定替代，不默认修改别人或 fork 的分支。
- 默认分支已解决：停止实现，验证后引用证据并关闭 issue。

## 2. 开发前检查

- 读取仓库级和目录级开发指令。
- 已通过第 0 节 CLI 闸门；记录实际使用的 `git` / `gh` / `glab` 路径，没有把认证或权限问题回退到网页。
- 确认默认远端、base 分支和分支命名规范，不硬编码 `origin/main`。
- 检查当前工作区、其他 worktree、已有同名分支和未完成任务。
- 记录 base SHA、issue 状态和已有相关 PR/MR。
- 用户要求解决或修复 issue 时，默认按完整远端交付提前验证托管平台登录态、仓库映射、push、创建 PR/MR 和合并能力；实际合并闸门由 `$merge-pr` 检查。只有用户明确要求有限交付时才缩小授权边界。
- 确定复现方法、风险面和最小验收集合。

## 3. 实现检查

- 失败基线能够说明问题真实存在。
- 修复针对根因，不扩大无关重构。
- 新测试在旧行为上失败、在新行为上通过，或说明无法这样验证的原因。
- API/schema/config/权限变化具有兼容和迁移策略。
- 日志不泄露敏感数据，错误路径可诊断。
- 文档、示例和产品说明只在真实行为发生变化时同步更新。

## 4. 平台文案

创建或实质改写 Issue、PR/MR 前必须执行本 Skill 的平台文案规则。标题、正文和自定义小节默认使用简体中文；不要因为仓库旧文案、提交消息或模板示例是英文就改用英文。保留仓库强制模板、`Closes #<id>` 等平台关键字、代码标识、命令和原文证据，用中文解释其作用。

PR/MR 正文建议结构：

```markdown
## 为什么改
说明问题、触发场景和影响对象。

## 改动
- 说明关键行为变化和用户现在会看到什么。
- 只补充评审所需的实现与兼容细节。

## 验证
- 列出实际运行的命令和结果。
- 说明未覆盖区域。

## 风险与回滚
- 说明兼容、部署或迁移风险。
- 给出回滚方式。

## 关联
Closes #<id>
```

新建回归或后续 Issue 时，用短句和具体动词写清现象、最短复现步骤、期望结果、影响范围和可判断真假的验收标准；根因尚未确认时明确写“待确认”，不要把猜测写成事实。不要用“优化体验”“完善逻辑”等空话，也不要用 commit 列表或测试命令代替解释。

创建前复查标题与第一段是否让不了解实现背景的人也能看懂，并核对 `base...HEAD` 的提交、文件和 diff，确保文案与真实改动一致且没有夹带其他任务。

## 5. 完成交付

- 创建或复用 PR/MR 后已立即进入 `$merge-pr`，没有把 PR/MR URL 当作完成结果。
- PR/MR 开放期间，每次 issue/PR 新评论、review、提交、检查完成或 base/head 漂移后都重新读取权威状态。范围内新口径已实现并重新验证，可修复的冲突或失败未被当作停止理由。
- 本流程创建并验证的 PR/MR 已按 `$merge-pr` 交付合并模式复用本地检查并通过 required checks、review 和平台策略。复用外部已有 PR/MR 时已按 PR 处理模式完成检查。
- 最终结果已进入目标分支，记录 merge/squash commit SHA。
- issue 已自动关闭；若未自动关闭，已留下提交/PR 与验证证据并主动关闭。
- 关闭后重新读取 issue，确认最终状态为 `CLOSED` 且关闭原因正确；否则任务仍未完成。
- 合并路径复用 `$merge-pr` 返回的 `$commit` 收口结果；未进入 PR/MR 路径或按用户明确边界暂停时，调用 `$commit` 的远端已完成模式盘点和安全清理，不触发新的远端交付。
- 本流程创建且已不活跃的远端分支、本地分支和 worktree 已删除并复查；开放 PR/MR 或明确后续任务仍需使用的现场保留并说明活跃证据。
- 无法合并或关闭时把恢复本 issue 必需的 AI 现场标记为活跃并给出恢复条件；用户或归属不明现场保持原样并报告。

必需平台检查 pending 时使用可用的等待/监控机制，恢复后重新读取 PR/MR、issue 讨论、精确 head SHA、检查和 review，不能沿用旧的绿色结论。只有用户明确要求只创建请求或暂停时才可以在此交付，并记录 PR/MR URL、精确 head SHA、最后检查时间、恢复条件以及“issue 尚未完成”。
