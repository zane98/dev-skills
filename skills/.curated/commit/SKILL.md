# Commit

交付当前请求授权的成果，并清理本任务已确认可删除的现场。其他任务的分支、stash、worktree 和用户 WIP 不属于默认清理范围；只有它们实际妨碍本任务安全操作时才构成阻塞。

## 模式与完成条件

- **默认交付**：按可独立评审、验证和回滚的语义边界划分一个或多个交付组，分别 commit、普通 push、创建 PR/MR，并通过 `$merge-pr` 的“交付合并”模式依次合并。全部授权组完成后验证本任务收口。
- **仅提交**：用户要求 `commit only`、停在 commit 或上层流程明确调用时，只提交；不隐含 push、合并或清理。用户说“不清理”时保留其余已授权交付步骤，仅跳过清理。
- **远端已完成**：供 `$merge-pr` 等上层流程在已合并或明确暂停远端交付后调用，只执行本任务本地收口，不再创建或合并 PR/MR；暂停时保留恢复所需现场并报告未完成。
- **仅清理**：不创建交付，按用户点名范围清理；“清理这个任务”仅处理本任务。只有明确要求“全仓清理／只保留目标分支”等全仓结果时，才对所有本地现场盘点、协调并执行 `verify-closeout`。

默认完成需要：各授权组的平台合并状态与 merge SHA 已确认；目标分支在安全可用的 checkout 中以 fast-forward-only 同步，未检出时使用绑定旧 SHA 的 CAS 快进；本任务清理清单中的资源已移除，`verify-task-closeout` 通过。本地同步未完成应单独报告，不得写成全部完成。其他任务现场原地保留，不把它们列为本任务失败。仅提交或远端受阻时报告准确停点。

全仓清理另需满足：只保留目标分支和主 worktree；主 worktree 位于目标分支且同步；stash、Git 进行中状态、tracked 改动、未忽略内容和任务临时路径均为空。任何不能安全处置的全仓范围项目都使全仓清理未完成，禁止为了验收清零而删除活跃或独有内容。

## 核心规则

1. 先只读盘点仓库级 branch、stash、worktree、进行中状态和临时路径，并按 checklist 核对目标 SHA、合并证据及真实远端开发分支；**盘点和报告覆盖全仓，删除仍按授权范围**。继承并核对上游及子 agent 的完整任务资源清单，补入本流程新建项并记录删除前 SHA/状态指纹；不得因切换 skill 或只看当前 cwd 漏项，也不得为使验收通过而从清单移除残留项。
2. 只删除同时满足“在授权清理范围内”和“证据支持可删除”的内容。可删除依据为已交付到目标、patch 等价、确认无用途或明确废弃授权。名称、时间或 dirty 状态不能证明归属或用途；开放 issue/PR/MR、用户保留指令、运行中的 owner 是活跃证据。范围内独有、未知或活跃项先协调，无法安全处理则报告该项未完成；范围外原地保留。
3. 不修改其他任务或用户的 index、hunk、worktree 和历史。同文件混合只 stage 已确认的本组 hunk。共享 checkout 正在被占用时，使用不冲突的任务 worktree 或等待实际依赖，不强制切分支、reset、清空 stash。
4. 普通 Git 现场删除使用 [git_cleanup.py](scripts/git_cleanup.py) 的 SHA/状态指纹参数；app-managed worktree 按 checklist 使用官方归档工具。状态漂移后重新盘点和判断。`clean-worktree` 会丢弃整个 worktree 改动，只能用于范围内、独占且全部内容已确认可删除的 worktree，不能用于混合 WIP。
5. 普通 ignored 构建产物、缓存、依赖、本地配置不作为独立清理目标；删除整个 worktree 前仍需核对其中 ignored 内容，保存确需保留的本地配置、独有素材等。本任务临时路径即使命中 `.gitignore` 也需记录和收口。自动发现的 `task_path_candidates` 只是候选。禁止全仓 `git clean -x`；不创建 quarantine、recovery ref 或归档副本来伪造完成；官方归档产生的可恢复快照不作为代码已交付的证明。
6. 默认授权当前请求内各交付组的普通 push、创建 PR/MR 和通过平台闸门后的合并，不授权来源不明内容进入交付、丢弃独有内容、强推或绕过 review、branch protection、merge queue。禁止直接推送目标分支。
7. 每组代码评审和本地检查由本流程完成，复用仍有效的结果；遇到实现缺陷、测试/hook/构建失败时，按 `$development` 的 [执行边界](../development/references/execution-boundaries.md) 直接修复并补受影响验证，再继续提交，不因处于 commit 阶段重新询问。用户明确禁止修改时照办。`$merge-pr` 接力核对精确 head/base、required checks、review、冲突和原子合并闸门，不重复有效本地验证。默认不使用 `[skip ci]`，不主动重跑非必需 CI。
8. 托管平台操作先验证 CLI、认证和仓库映射。GitHub 使用 `gh`，不足时 `gh api`；GitLab 使用 `glab` 及其 API。权限或认证失败不能用网页绕过；仅用户明确要求网页操作时使用浏览器。
9. PR/MR 标题、正文和自定义小节默认简体中文，保留仓库模板、平台关键字和代码标识。先说问题与行为变化，再写实际验证、必要风险和回滚；不要堆砌 commit 或命令。凭据只报告路径类别，不展示 secret。

## 工作流

执行前读取 [commit-checklist.md](references/commit-checklist.md)，其中包含平台检查、删除命令和 scope manifest 契约。

### 1. 确认并提交交付组

识别仓库、平台、目标分支、授权范围和规范；feature upstream 不等于合并目标，优先已有 PR/MR base、远端默认分支和仓库规则。记录各组文件/hunk、验证和顺序。若在目标分支上，先创建任务分支。逐组检查 diff、secret、大文件及边界，运行风险匹配的本地测试，复查 staged diff 后提交；没有改动时确认是否已有 commit，禁止空提交。当前 checkout 无改动不代表其他分支已交付，仍须完成现场状态报告。

每组记录接力上下文：仓库、目标分支、已验证 base SHA、head 分支与精确 head SHA、已评审 diff 范围、实际测试及结果。当前组与其他待交付组保持独立，避免把后续输入当作残留清除。

### 2. 远端交付

确认任务分支所有权和 push 权限后普通 push，并核对远端 head SHA。复用仓库/head/base/SHA 匹配的开放 PR/MR，否则创建。立即加载并执行 `$merge-pr` 的“交付合并”模式，传入 URL、接力上下文及合并后清理符合安全条件的同仓库远端 head 的授权；创建 PR/MR 不是结束点。

由 `$merge-pr` 完成平台闸门与合并。确认状态和 merge SHA 后，在不影响其他任务的 checkout 中以 fast-forward-only 同步目标，再从最新目标建立下一组，不让后续 PR/MR 依赖已删除 head。工具、认证、权限或平台能力受阻时保留可恢复成果并报告，不退化为直接推送目标。

重复以上步骤直到所有授权组完成，再进入最终收口。组间不运行最终清理。

### 3. 按任务范围收口

从全过程记录和当前盘点形成 scope manifest；核对继承现场与新建现场的每项去向，不只核对当前分支。分支按本地名称、stash 按完整 SHA、worktree/临时路径按绝对路径记录；只纳入本任务应移除的资源，另保留活跃/未交付现场及其理由。主 checkout 中本任务改动应已提交或有明确处置依据，其他 WIP 保留。资源清单不能替代 diff 归属和交付检查。

恢复已有交付时，可依据原任务/附件记录和精确 repo、PR/MR、base/head SHA、branch/worktree 路径显式接管同任务现场；先核对当前新增提交、dirty 内容及 owner 已释放，再纳入清单。仅名称相同或历史 PR 已合并不能证明同任务归属或当前内容已交付。

逐项确认可删除依据，先从待删除 worktree 切换到仍存在的安全 checkout/cwd，再移除或官方归档任务 worktree，删除任务分支、按实时 selector 和 SHA 删除任务 stash，最后删除任务临时路径。保留每项删除前指纹和结果。候选属于其他任务或归属不明时不删；若本任务操作不依赖其去留，继续收口。范围内现场仍活跃时协调该 owner，不能安全删除就明确未完成。

全仓清理只在明确授权时扩大到全仓，使用相同所有权、活跃性和指纹闸门；不得把“全仓”解释为丢弃未知内容的授权。

### 4. 验证和报告

默认执行 `git_cleanup.py verify-task-closeout --repo <repo> --manifest <scope.json>`；全仓清理另执行 `verify-closeout --repo <repo> --target <target>`。前者只证明清单所列本地资源不存在，不能证明清单完整、任务 diff 已交付、远端合并或全仓干净；必须结合交付上下文和操作记录报告。

最终逐组明确 `已合并并清理`、`已合并但同步/清理未完成` 或 `尚未合并，保留现场`，附 commit、PR/MR、merge SHA 和实际验证；清理无交付的临时现场时写明 `无需合并，已清理`。列出任务资源的删除/归档结果或保留路径、理由与下一步。

另外逐项报告全部额外本地分支/worktree及同仓库真实远端开发分支，允许将同 SHA 的对应现场合并为一行：`分支/路径 | 目标及 PR/MR | 合并证据或未知 | 新增提交/dirty | 删除、归档或保留理由`。范围外保留仍需可见；平台或 owner 无法核实时标明未知及缺少的证据。零资源验收必须同时说明额外现场哪些已纳入目标、尚未合并或状态未知，不能只报“收口通过”。不要把任务范围通过说成全仓零残留，也不把未同步或未清理包装成完整交付成功。
