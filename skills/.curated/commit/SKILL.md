# Commit

提交当前成果，通过托管平台 PR/MR 合并到目标分支，然后删除已确认失去用途的 AI 开发现场；用户内容和归属不明的现场保留并报告。

## 模式

- **默认交付**：用户要求 commit 或结束任务时，视为授权把当前任务提交、普通 push 到任务分支、创建 PR/MR，并在所有闸门通过后合并到目标分支；随后清理已确认由 AI 创建且不再活跃的现场。
- **仅提交**：用户明确要求 `commit only`、不清理或停在 commit 时使用；`$resolve-issue` 等上层流程也可在中途提交阶段明确调用此模式。
- **远端已完成**：仅供 `$merge-pr` 等上层流程在已经合并或明确暂停远端交付后调用；不再 push、创建或合并 PR/MR，只执行本地盘点和安全清理，防止流程递归。
- **全仓清理**：只有用户明确要求清理整个仓库时，才盘点全部本地现场；仍只删除能证明属于 AI 开发且已失去用途的内容。

## 最终不变量

- 默认模式下，当前交付已提交并通过 PR/MR 合并到目标分支，平台状态与最终 merge SHA 已确认；仅提交或受阻时明确报告停点。
- 当前任务没有遗留未提交内容。
- 已确认由 AI 创建的分支、stash、额外 worktree 和临时内容都有活跃任务，否则已经删除。
- `.gitignore` 覆盖的构建产物、缓存、依赖和本地配置保持原样，不以工作区磁盘整洁作为提交验收条件。
- 用户内容和归属不明的现场未被修改，并在最终回复中列出。
- 不创建 quarantine、recovery ref 或归档副本。

## 活跃证据

只有以下情况算活跃：当前请求正在使用；存在匹配的开放 issue/PR/MR 且计划继续；用户明确要求保留；能够确认由仍在运行的 agent、自动化或人工任务占用。名称像 `wip`、修改时间较新或“可能有用”不算活跃证据，也不能单独证明内容由 AI 创建。

## 核心规则

1. 先盘点再删除，读取仓库指令、托管平台状态和所有 worktree。
2. 删除必须同时具备 AI 所有权证据和“不再活跃”证据；缺任一项就保留并报告。
3. 不归档、不隔离、不创建 recovery ref，也不移动归属不明内容。
4. 使用 [git_cleanup.py](scripts/git_cleanup.py) 的 SHA/状态指纹参数执行删除；状态漂移时重新盘点。
5. 只提交当前任务相关内容，不改写其他任务或用户的 index、worktree 和历史。
6. 不输出 secret；疑似凭据只报告路径类别，未获明确授权不展示或移动。
7. 默认不强推、不改写共享分支，也不直接把交付推到目标分支；在任务分支普通 push 后创建 PR/MR，并调用 `$merge-pr` 的交付合并完成平台闸门、合并与远端 head 清理。
8. 将 ignored 内容视为开发环境，不在 commit 收口中删除；只有用户明确点名路径并要求清理时，才单独处理。
9. 用户调用默认 `$commit` 即授权本次任务的普通 push、创建 PR/MR，并在仓库闸门通过后合并；不代表授权绕过 review、CI、branch protection、merge queue 或强推。
10. 所有由默认 `$commit` 创建或复用的 PR/MR 都必须显式触发 `$merge-pr` 的“交付合并”模式；“已创建 PR/MR”不是完成状态，不得只返回链接或把合并留给用户。
11. 代码评审和本地测试只由 `$commit` 执行一次；交付合并中的 `$merge-pr` 不做代码检查。平台 CI、review、branch protection 与原子合并仍必须执行，它们是远端状态和权限闸门。

## 工作流

执行前完整读取 [commit-checklist.md](references/commit-checklist.md)。

### 1. 确认交付

识别 Git 根目录、托管平台、目标分支、当前任务和仓库规范。feature upstream 不等于合并目标；优先使用已有 PR/MR base、远端默认分支和仓库规则。若当前位于目标分支且成果尚未提交，先创建任务分支再提交，禁止直接推送目标分支。

检查当前任务 diff、secret、大文件和提交边界，运行匹配风险的测试。同文件混合时只 stage 当前任务 hunk；无法确认归属的 hunk 不提交、不丢弃。复查 staged diff 后提交当前交付。没有可提交改动时，先判断当前任务 commit 是否已经存在，禁止制造空提交。

提交后记录交付合并上下文：仓库、目标分支、已验证 base SHA、head 分支、精确 head SHA、已评审 diff 范围，以及实际运行的测试和结果。

### 2. 远端交付

确认 remote、认证和任务分支所有权后，以普通 push 发布当前任务分支并绑定预期 head SHA；禁止强推。复用 head/base/SHA 匹配的现有开放 PR/MR，否则创建新的 PR/MR，标题和正文说明改动与验证结果。

PR/MR 创建或复用成功后，立即显式加载并执行 `$merge-pr` 的“交付合并”模式，传入 PR/MR URL 和交付合并上下文。所有默认 `$commit` 交付一律使用该模式，必须在当前任务内继续执行，不能停在 PR/MR 创建状态。

由 `$merge-pr` 按“交付合并”模式只核对交付上下文与 head/base SHA，等待必需 CI、review、merge queue 和平台策略，再按仓库规定方式合并；不得重新评审代码、读取完整 diff 或运行本地测试。head/base 漂移、冲突解决产生新 head 或平台重跑检查时，继续只处理平台状态和合并，不把流程切换为 PR 处理模式。缺少 skill、remote、认证、权限或托管平台能力时保留已完成成果，明确报告阻塞与恢复步骤；不得假装已触发、把合并留给用户或退化为直接推送目标分支。

### 3. 全仓盘点

使用 cleanup helper 获取本地 branch、stash、worktree、Git 进行中状态和状态指纹；同时检查远端开放 issue/PR/MR、live agent/automation 和未忽略临时目录。ignored 内容只用于识别本地环境，不进入清理候选。为其他候选项分别记录所有权与活跃性证据。

### 4. 直接清理

按 checklist 的依赖顺序，只删除同时满足所有权和活跃性条件的候选项；不对 ignored 内容运行 `git clean -x` 或逐路径删除。远端真实分支只按 `$merge-pr` 规则处理。不要为被删内容建立副本；删除失败或状态变化时重新盘点，不升级为无条件强制删除。

### 5. 验证

重新盘点并确认最终不变量。仍存在的 AI 现场必须对应活跃任务；用户内容或归属不明现场保留并报告，不把“仓库不完全干净”伪装成已彻底清理。

## 最终回复

必须包含：

- 目标分支、commit SHA、任务分支与 push 状态、PR/MR URL、检查结果、合并方式和最终 merge SHA
- 删除的 branch、stash、worktree、临时路径及其 AI 所有权、非活跃证据和删除前指纹
- 保留的活跃 AI 现场，以及归属不明或用户现场
- 当前工作区、分支、stash、worktree 和 remote-tracking refs 最终状态
- 明确说明未创建归档、隔离或恢复副本
