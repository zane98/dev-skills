# 阿里云部署

先读取项目部署脚本、Compose、Runbook 和远端 manifest，复用真实发布路径。项目约定优先，不预设只有 production、不预设 CPU 架构或必须本地构建。

## 确定目标与授权

- 用户要求诊断时只读取证；发布/回滚时确认目标环境、主机、目录、域名、镜像与源版本。未指定环境且项目存在多个可写目标时，先定位并请求必要决策，不能默认发布到生产。
- SSH 身份与密钥使用已有配置，不重复索要可查到的信息，不输出秘密。区分应用数据与凭据的存储用途。
- 从目标平台和现有流水线确定镜像架构、本地/CI/远端构建以及上传或 registry 拉取方式；不临时另建发布体系。
- 部署授权不包含新的 Git 交付、无关环境变更或全仓清理。目标内必要代码修复由 $development 处理；产品行为或破坏性数据范围发生变化时重新定界。
- 复杂代码迁移用 $development-plan 拆实现依赖；发布顺序、观察、备份和恢复执行放项目 Runbook，不混入开发计划。

## 执行与证明

1. 核对本地 Git/dirty 状态、目标与当前部署来源，记录本次实际源版本及预期变更。
2. 按项目脚本构建、推送/上传并加载镜像；使用确定性 tag 或 digest，保留可用的恢复版本。
3. 仅在本次需要且授权覆盖时执行迁移，明确兼容顺序、重试与中断恢复；没有 migration 变化不制造迁移步骤。
4. 启动或更新目标服务，观察命令最终结果、容器/readiness、应用健康与用户相关公开路由。
5. 核对 manifest、镜像和实际运行版本，区分源码、迁移、服务启动、业务路由和外部 provider 的证据；资金或通知完成不能由 HTTP 200 代替。

远端操作按资源与副作用控制并发；同一部署、迁移和共享状态串行，低成本独立读取可并行。正在重试的发布继续跟踪原进程，不因等待超时启动第二次发布。

## 排障与恢复

- 先定位失败阶段，读取对应容器日志、健康、manifest、磁盘/资源及依赖状态；不把历史告警自动当成本次发布失败。
- 镜像回退前判断新 schema、消息、缓存与外部副作用的兼容性；迁移已执行时不盲目 downgrade，按项目恢复方案选择回退或前向修复。
- 发布未完成时报告实际停点与恢复动作；通知仅在用户已授权时由对应通知 skill 发送，并另行核对发送结果。
