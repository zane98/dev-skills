# Development Plan

把复杂需求变成能施工、能跟踪、能验收的活计划；与 `$development` 叠加。用户只要求计划或方案时，交付计划后停止，不自行开工。

## 计划硬约束

- 先区分已确认事实、暂定假设、待确认项和非目标；非阻塞信息采用明确且可逆的假设，足以改变方案的分歧才请求用户决策。
- 涉及前后端、外部调用或跨模块契约时先定协议与唯一来源；没有契约变化时不为形式创建 API 阶段。
- 涉及后端时，计划覆盖数据、服务、权限、缓存/队列、测试和可观测性影响。
- 涉及前端时，计划覆盖相关用户端、管理员端、员工端或其他角色端。
- 权限是横切项：角色、入口、接口权限、数据权限和操作审计都要检查。
- 计划按真实依赖分层；任务使用稳定 ID，记录负责人、输入、输出、依赖、并行关系和验证方式。
- 验收条件必须写成“验证对象 + 操作或检查 + 预期结果”；只有输出存在且验证证据通过时才能标记 `done`。
- 持续记录 `todo / doing / blocked / done / cancelled`；阻塞项写清原因、解除条件和责任人，范围变化保留决策记录。
- 涉及破坏性变更、不可逆数据、高风险业务或生产拓扑时，覆盖迁移、发布顺序、观测、回滚条件和恢复验证。
- 优先可执行、简洁、易改；不追求大而全。

## 标准阶段

按需使用边界、契约、后端、前端、联调、迁移发布和验收阶段；真实依赖、阶段门槛与多端检查见 `references/phase-breakdown.md`。

删除不适用阶段，不为凑模板制造工作。

## 输出位置

- 单层、单次完成且不需要持续跟踪的计划可直接在回复中给出。
- 跨层、超过 5 个任务、多人并行或需要跨轮次执行的计划写入 `docs/plans/{feature}/README.md`，作为进度与决策的唯一总入口；执行期间同步当前任务、阻塞、证据和范围变化。
- 大需求按实际范围拆分 `01-api.md`、`02-backend.md`、`03-frontend.md`、`04-test-acceptance.md`、`05-release.md`，不创建空文件。
- 已有项目计划目录或 AGENTS.md 有约定时，优先遵循项目约定。

## Reference 选择

- 需要落文件或输出完整计划时，读 `references/plan-template.md`。
- 需要定义前后端协议时，读 `references/api-first.md`。
- 需要拆阶段、排依赖、覆盖多端时，读 `references/phase-breakdown.md`。
- 需要多人/多 agent 并行或持续记录进度时，读 `references/task-parallel.md`。
- 涉及迁移、破坏性变更、高风险业务或生产发布时，读 `references/delivery-safety.md`。
