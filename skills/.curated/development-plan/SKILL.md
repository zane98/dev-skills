# Development Plan

把复杂需求拆成能实现、能跟踪的开发计划；与 `$development` 叠加。用户只要求计划或方案时，交付计划后停止，不自行开工。

## 计划硬约束

- 先区分已确认事实、暂定假设、待确认项和非目标；非阻塞信息采用明确且可逆的假设，足以改变方案的分歧才请求用户决策。
- 涉及前后端、外部调用或跨模块契约时先定协议与唯一来源；没有契约变化时不为形式创建 API 阶段。
- 涉及后端时，计划覆盖数据、服务、权限、缓存/队列、测试和可观测性影响。
- 涉及前端时，计划覆盖相关用户端、管理员端、员工端或其他角色端。
- 权限是横切项：角色、入口、接口权限、数据权限和操作审计都要检查。
- 只记录开发产出与真实依赖：代码、契约、schema/migration、配置、必要测试资产和长期文档。Git 交付、部署、共享环境迁移执行、线上验证及人工验收不属于开发计划，不进入任务、阶段、依赖或完成条件；测试/构建的运行记录也不回填计划。
- 任务保留 ID、输出、状态、负责人、依赖和影响范围；使用 todo / doing / blocked / done / cancelled。状态只反映开发缺口：缺少会改变实现的决策可以 blocked；等待合并、部署、主观界面确认或线上验证，不能使已完成开发保持或退回 doing/blocked。
- 开发产出完成且按 $development 处理必要检查后标 done；代码缺陷、缺失契约/测试资产仍按开发任务修复，不能用“部署不在范围”跳过实现所需验证。运行中发现的问题继续按 $development 处理，不另建验证流水任务。
- 全部实现任务 done/cancelled 且无开发 blocker 时，总体开发状态为 done 并归档，与整个 Issue/Git/发布流程的状态分别维护。用户问计划是否完成时按开发任务回答，不把尚未部署或线上验证列为计划欠项。后续新缺陷建新任务，不重开归档计划追加历史。
- 按真实依赖分层，任务 ID 创建后保持稳定；范围变化保留必要决策。
- 涉及破坏性变更、不可逆数据或高风险业务时，覆盖迁移、幂等、可观测性与恢复能力的代码产出；执行发布、观察及生产恢复使用独立 Runbook。
- 优先可执行、简洁、易改；不追求大而全。

## 标准阶段

按真实依赖拆分契约、数据/后端、前端和集成实现；迁移脚本、测试资产、配置及长期文档纳入相应实现任务。拆分与状态推进见 `references/phase-breakdown.md`。

删除不适用阶段，不为凑模板制造工作。

## 输出位置

- 单次完成且不需要持续跟踪的计划可直接在回复中给出；需要持久化时沿用项目目录，一个目标默认一个计划文件。
- 开发完成后移入 `done/`，同步旧入口、索引和完成状态，只保留一个当前事实源；不能只新建完成版，却让旧入口继续指向 doing。项目长期导航保留并更新链接，已无活跃任务的临时协调索引移除。
- 未提交不等于范围外：同任务旧计划先核对差异、保留独有内容，再归并或更新入口；归属不明或另有活跃写入的内容不覆盖，明确报告文档同步未完成，不能把它解释为开发仍在 doing。
- 只有可独立交付、明确负责人且能降低冲突的实现流才拆文件；不创建验收、发布、验证流水或历史记录分片。
- 长期产品与架构事实进入权威文档；发布顺序、灰度、观察和生产恢复进入 Runbook。

## Reference 选择

- 需要落文件或输出完整计划时，读 `references/plan-template.md`。
- 需要定义前后端协议时，读 `references/api-first.md`。
- 需要拆阶段、排依赖、覆盖多端时，读 `references/phase-breakdown.md`。
- 需要多人/多 agent 并行或持续记录进度时，读 `references/task-parallel.md`。
- 涉及迁移、破坏性变更或高风险恢复代码时，读 `references/delivery-safety.md`。
- 修改计划范围或状态判断时，使用 [完成口径回归场景](evaluations/completion-routing.json)；行为回放只提供 prompt，隐藏预期结果。
