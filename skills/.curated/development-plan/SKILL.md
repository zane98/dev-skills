# Development Plan

把已确定的方案拆为最少必要的实现任务。产品与架构取舍由 $development 负责，计划不替代设计判断。用户只要计划时交付计划后停止。

## 任务与状态

- 只记录开发产出与真实依赖：代码、契约、schema/migration、配置、必要测试资产和长期文档。Git 交付、部署、共享环境迁移执行、线上验证及人工验收不属于开发计划，不进入任务、阶段、依赖或完成条件；测试/构建的运行记录也不回填计划。
- 任务保留 ID、输出、状态、负责人、依赖和影响范围；使用 todo / doing / blocked / done / cancelled。状态只反映开发缺口：缺少会改变实现的决策可以 blocked；等待合并、部署、主观界面确认或线上验证，不能使已完成开发保持或退回 doing/blocked。
- 开发产出完成且按 $development 处理必要检查后标 done；代码缺陷、缺失契约/测试资产仍按开发任务修复，不能用“部署不在范围”跳过实现所需验证。运行中发现的问题继续按 $development 处理，不另建验证流水任务。
- 全部实现任务 done/cancelled 且无开发 blocker 时，总体开发状态为 done 并归档，与整个 Issue/Git/发布流程的状态分别维护。用户问计划是否完成时按开发任务回答，不把尚未部署或线上验证列为计划欠项。后续新缺陷建新任务，不重开归档计划追加历史。

## 拆分与文件

- 按真实依赖确定契约、数据/后端、前端和集成顺序，不为凑阶段制造 API、测试或文档任务。资金、权限、并发、兼容和恢复是对应实现任务的横切要求。
- 默认在对话中给计划；用户要求持久化/跨轮次跟踪或项目约定需要时，一个目标默认一个文件，沿用项目目录。归档到 done/ 时同步旧入口、索引和完成状态，只保留一个当前事实源。不能只新建完成版，却让旧入口继续指向 doing。
- 未提交不等于范围外：同任务旧计划先核对差异、保留独有内容，再归并或更新入口；归属不明或另有活跃写入的内容不覆盖，明确报告文档同步未完成，不能把它解释为开发仍在 doing。
- 仅有可独立交付、明确负责人且能降低冲突的实现流时拆文件。两个以上活跃计划确需协调时可有临时索引；不索引历史计划，最后一个计划归档后移除临时索引。
- 长期产品/架构事实进入权威文档；发布顺序、灰度、观察和生产恢复进入 Runbook。

## 并行

- 仅在两个以上任务依赖已满足、范围清楚且预计缩短总关键路径时使用少量子 agent；用户只要计划时不启动实施型 agent。
- 每个子 agent 负责一个可完成任务，明确输入、输出、允许路径、共享文件所有者和检查要求。主 agent 负责共享契约、集成和计划状态；进一步委派仍须遵守既定范围、可用槽位和写入所有权，不能自行扩展目标。
- 仅用户或更高层明确要求 goal 时使用 goal 工具；普通任务提示中的 objective 已足够，不额外创建另一套状态。用户未给 token 预算时不设置预算。
- 结果返回后主 agent 检查实际产出、契约和必要验证再更新任务；有重叠或依赖变化时协调或串行，不等最后合并碰运气。
