# API First

## 为什么先 API

涉及前后端、外部调用或跨模块 API 时，先稳定协议并指定唯一来源。后端按契约实现，前端可用隔离的 mock fixture 并行开发，联调时少猜谜；没有契约变化时不创建空 API 阶段。

## API 计划必须包含

- 调用方：用户端、管理员端、员工端、第三方或后台任务。
- 唯一来源：OpenAPI、schema、共享类型或项目已有契约文件；不要维护互相漂移的重复定义。
- 接口路径、方法、鉴权方式和权限要求。
- 请求参数：类型、必填、默认值、枚举、范围、分页、排序。
- 响应结构：字段语义、空值规则、列表结构、分页结构。
- 错误语义：参数错误、未登录、无权限、资源不存在、冲突、系统错误。
- 幂等性：创建、提交、支付、回调、导入、队列触发必须考虑重复请求。
- 运行边界：超时、重试、限流、并发和第三方失败策略，按风险选择。
- 兼容性：新增字段、删除字段、字段语义变化、版本迁移。
- mock fixture：与契约一致，只用于测试、Storybook 或隔离开发环境，不进入生产路径；后端未完成时明确记录 `pending-backend`。

## API 阶段完成标准

- 契约唯一来源已确定，schema、契约检查或等价验证通过。
- 调用方能明确字段、空值和错误语义，权限边界清楚。
- 前端能基于隔离 mock 开始实现，且未把 API 阶段完成误报为端到端完成。
- 后端能基于契约实现 service 和测试。

契约检查、typecheck 和联调由 `$development` 在执行过程中完成，不另建计划任务或写入计划证据字段。
