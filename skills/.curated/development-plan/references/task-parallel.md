# Task Parallel

## 状态

- `todo`：已识别，未开始。
- `doing`：正在执行。
- `blocked`：有明确阻塞，写清等待什么。
- `done`：已完成并通过对应验证。
- `cancelled`：因范围或决策变化取消，保留原因和替代任务，不删除历史。

## 任务拆分

每个任务必须包含：

- ID：使用 `REQ/API/DATA/BE/FE/QA/REL` 等稳定前缀，创建后不重编号。
- 目标：完成什么。
- 输入：依赖的 API、设计、数据、权限或文档。
- 输出：代码、文档、测试、隔离 mock fixture 或验收项。
- 依赖：前置任务。
- 验证：写成验证对象、操作或检查、预期结果。

负责人、风险或范围明确时一并记录。任务只有在输出存在且验证证据符合预期时才能标记 `done`。

## 并行规则

- 涉及跨端 API 时，契约定稿前只并行做边界确认、验收清单、原型或技术调研。
- 涉及跨端 API 时，契约定稿后后端和前端可以并行；没有 API 依赖时按真实前置条件拆分。
- 后端内部可拆数据模型、service、队列/缓存、测试。
- 前端内部可拆用户端、管理员端、员工端/其他角色端。
- 涉及 API 时，联调前必须合并契约变更和关键后端接口。
- 同一迁移、schema、公共契约或高冲突文件的任务不得盲目并行；先划分所有权或执行顺序。
- 不因为任务能分给不同人就判定可并行；只按真实数据、契约和文件冲突判断。

## 进度维护

- 每次执行后更新当前任务、状态、验证证据和新阻塞，不把计划留成出土文物。
- `blocked` 记录原因、解除条件和责任人；解除后恢复为 `todo` 或 `doing`。
- 范围或关键方案变化时追加决策记录，受影响任务改为 `cancelled` 或新增任务，不覆写历史。
- 总文档只保留状态摘要和任务索引；细节写入拆分文档，避免重复维护两份真相。
