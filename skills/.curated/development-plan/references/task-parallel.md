# Task Parallel

## 状态

- `todo`：已识别，未开始。
- `doing`：正在实现，或实现相关检查失败后仍需修正。
- `blocked`：缺失会阻止实现继续的开发输入，写清解除条件和责任人。
- `done`：开发输出完成，已按 `$development` 处理必要检查。
- `cancelled`：因范围或决策变化取消，保留原因和替代任务，不删除历史。

等待提交、合并、部署、主观界面确认或线上验证不进入以上状态；开发完成与 Git/发布进度分别维护。

## 任务拆分

每个任务必须包含：

- ID：使用 `REQ/API/DATA/BE/FE/TEST/DOC` 等稳定前缀，创建后不重编号。
- 目标：完成什么。
- 输入：依赖的 API、设计、数据、权限或文档。
- 输出：代码、契约、schema/migration、配置、长期文档或测试资产。
- 依赖：前置任务。

负责人、风险或范围明确时一并记录。运行检查不是计划任务，检查证据留在对话、PR 或 CI；新增测试代码或可复用工具才属于实现产出。

## 并行规则

- 涉及跨端 API 时，契约定稿前只并行做边界确认、测试资产、原型或技术调研。
- 涉及跨端 API 时，契约定稿后后端和前端可以并行；没有 API 依赖时按真实前置条件拆分。
- 后端内部可拆数据模型、service、队列/缓存、测试。
- 前端内部可拆用户端、管理员端、员工端/其他角色端。
- 涉及 API 时，联调前必须合并契约变更和关键后端接口。
- 同一迁移、schema、公共契约或高冲突文件的任务不得盲目并行；先划分所有权或执行顺序。
- 不因为任务能分给不同人就判定可并行；只按真实数据、契约和文件冲突判断。

## 进度维护

- 更新当前实现任务、开发状态与开发阻塞，保持唯一事实源；不回填执行日志和验证证据。
- `blocked` 记录原因、解除条件和责任人；解除后恢复为 `todo` 或 `doing`。
- 范围或关键方案变化时追加决策记录，受影响任务改为 `cancelled` 或新增任务，不覆写历史。
- 拆分计划的总入口只保留开发状态和活跃任务索引；全部完成后归档并同步旧入口。同任务未提交旧草稿先比对、保留独有内容再归并，不留下旧 doing 入口。
