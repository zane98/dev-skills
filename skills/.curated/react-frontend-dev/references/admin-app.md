# Admin App Rules

在管理后台、运营平台、内部工具、B 端控制台中，默认采用以下策略：

- 组件优先级：项目已有后台组件 > `antd` > 新建后台业务组件
- 表单优先级：项目已有后台表单封装 > `antd` Form
- 不默认使用 `shadcn/ui` 构建后台主界面，除非仓库现状已经明确采用该体系
- 优先保持信息密度、操作效率、一致性和可维护性，而不是追求前台式视觉表达
- 后台页面本身要承担表达职责，默认不要堆欢迎语、解释性段落、使用说明卡；需要说明时也应短、贴近动作、贴近控件
- 表格、表单、筛选器、分页、批量操作、Drawer、Modal、Result 页优先基于 `antd` 生态和项目已有封装
- 列表页和详情页要统一查询参数、筛选态、分页态、批量操作反馈
- 危险操作必须有确认机制，异步操作必须有清晰的进行中与结果反馈
- 管理后台不强制把筛选、分页、排序同步到 URL；只有在分享链接、返回恢复或产品要求明确时再接入 `search params`
- 关键列表区块、详情区块和提交流程仍应有统一错误提示、空态和错误态；是否提供重试按真实操作特征决定
- 后台 header 默认控制在 `48px` 到 `64px`，优先 `48px` 或 `56px`，避免大面积空白吞掉首屏
- 后台界面默认保持扁平，优先使用分割线、分组标题、栅格和留白组织内容，而不是大量边框、卡片外框或装饰性阴影
- 后台主内容区默认不依赖阴影；浮层、下拉、抽屉、Modal 等需要表达悬浮关系时再谨慎使用极弱阴影

建议优先抽取：

- 列表页模板
- 查询表单与筛选栏
- 表格列定义辅助函数
- 权限守卫组件
- 标准化详情区块、描述列表、批量操作工具栏

不推荐的做法：

- 后台项目同时并行维护多套主 UI 组件体系
- 页面到处散落重复的列表查询、表格状态和弹窗提交逻辑
- 只图快，直接在页面里写长函数和临时状态
- 把后台页面做成大标题 + 大说明 + 大卡片 + 大阴影的演示稿风格
