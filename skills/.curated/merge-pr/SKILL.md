# Merge PR

把“能不能合”与“怎么合”分开处理：PR 处理入口先检查改动，交付合并入口复用上层验证，然后选择平台合并或本地冲突集成；远端合并后必须把结果合入本地目标分支，让后续开发从最新主线继续。

## 边界

- 从 issue 开始实现需求，使用 `$resolve-issue`。
- 本地提交和 AI 开发现场清理使用 `$commit`；本流程负责 PR/MR 评审、冲突、合并、本地目标分支同步和关联远端分支。
- 本流程只清理自己创建或由上游显式移交的同任务本地现场，以及与已合并 PR/MR 一一对应且可证明安全的远端分支；继承完整资源清单，不因接力漏掉开发 worktree。符合安全条件的同仓库 head 默认删除，保留必须有明确例外证据。
- 创建冲突替代 PR/MR 或实质改写请求正文时，标题、正文和自定义小节默认使用简体中文。用人话说明原请求、冲突处理、实际纳入范围、验证、风险和回滚，让不了解冲突背景的人也能看懂；保留原请求 URL、SHA、平台关键字和代码标识，不编造未确认的事实。
- 不绕过 required checks、必需 review、branch protection 或仓库合并策略；不主动触发或重跑非必需 CI。

## 平台工具闸门

- 先根据 remote 或 PR/MR URL 识别托管平台，再按 checklist 验证本地 CLI、登录身份与仓库映射。
- GitHub 检测到 `gh` 时，PR 定位、diff、required checks、review、评论、合并和 GraphQL/REST 查询必须使用 `gh`；高阶命令缺少能力时使用 `gh api` / `gh api graphql`，不得打开网页补操作。普通 Git ref 的 fetch/push 和带 lease 删除继续使用 `git`。
- GitLab 检测到 `glab` 时执行同样约束；需要的能力不在高阶命令中时使用平台 API。
- CLI 存在但未认证、权限不足、仓库映射失败或网络失败时，修复该条件或报告阻塞。不得调用 browser、Computer Use、网页登录或手工点击作为回退。
- 只有用户明确要求操作托管平台网页界面时才允许使用浏览器；用户只说 review、处理或合并 PR/MR 不构成网页授权。

## 模式

- **PR 处理**：用户直接要求“合并这个 PR/MR”“处理这个 PR/MR”或明确要求 review/审核/检查时使用，不因 PR 作者是用户自己而跳过。先完整检查代码，再处理冲突、平台闸门和合并。
- **交付合并**：仅由当前 `$commit` 或 `$resolve-issue` 流程为其刚创建并已验证的精确 head SHA 显式触发。不得重复检查代码、读取完整 diff 或运行本地测试；复用上层本地验证，只执行 required checks、review、branch protection、merge queue、权限和原子合并闸门。

只按入口选择模式，不按 PR 作者身份猜测。用户直接点名 PR 并要求合并或处理时始终使用 PR 处理；上层 `$commit` 或 `$resolve-issue` 在同一交付流程中携带验证上下文调用时使用交付合并。已有 PR、跨任务恢复或缺少上层验证上下文时使用 PR 处理。

两个模式的合并授权都默认包含合并后把远端目标分支拉取并合入本地对应分支，以及清理符合安全条件的同仓库 head 分支，用户无需额外说“拉取 main”或“删除分支”。本地目标分支包含最新远端结果是合并流程的硬完成条件：平台合并前先验证本地分支能够在保留现有代码的前提下继续前进；无法保证时停在平台合并前处置现场，不得先合远端再把本地同步降级为后续事项。禁止用 reset、rebase、自动 stash 或丢弃用户改动完成同步。只有用户明确要求保留，或分支属于 fork、仍被其他开放 PR/MR 使用、受保护、权限或归属不清、远端 SHA 已漂移、仍有明确活跃用途时才保留远端 head，并报告证据。

## 合并闸门

PR 处理模式只有 checklist 的需求、本地评审与测试、当前 head SHA、review、权限和仓库策略闸门全部通过才继续；GitLab 另包含必需 CI。交付合并模式只确认上层本地验证上下文、SHA 与远端闸门。默认 `$commit`、`$resolve-issue` 或用户直接要求合并已经授权对应模式下的合并；平台保护规则不能绕过。

## 工作流

执行前读取 [merge-checklist.md](references/merge-checklist.md)。

### 1. 定位 PR/MR

先通过平台工具闸门，再按 checklist 定位平台、项目、base/head、作者和最新 SHA，保护本地已有改动。根据调用入口选择模式；用户直接请求始终选择 PR 处理，当前 `$commit` 或 `$resolve-issue` 携带验证上下文接力时选择交付合并。处理不可信来源且没有隔离环境时只做静态评审。

### 2. 完成评审

PR 处理模式检查完整 diff、需求、正确性、安全、数据、兼容、测试和运维风险。用户要求处理或合并时，发现缺陷、可修复的检查失败或 review 问题，按 `$development` 的 [执行边界](../development/references/execution-boundaries.md) 直接修复、验证并继续；不以报告 findings 代替交付。用户只要求评审/审计时报告 findings，保持只读且不合并。

交付合并模式跳过本步骤，不读取完整 diff，也不运行任何本地测试。记录上层流程、验证上下文和 head/base SHA，直接进入合并路径。

### 3. 选择合并路径

- **无冲突**：复用当前 head 的本地检查并等待 required checks；按仓库规则并绑定预期 head SHA 合并，条件不满足时重新读取平台状态。
- **有冲突且可更新原 head**：在隔离 worktree 中从最新 PR head 创建临时集成分支，把最新 base 合入该分支并按双方意图解决冲突。冲突产生的新 head 运行一次受影响本地检查并重新等待 required checks。只有实际 branch push 权限、保护规则和仓库政策均允许，且远端 head SHA 未变化时，才把冲突解决提交以普通 fast-forward push 推回原 head。
- **有冲突但不能更新原 head**：从最新 base 创建自有集成分支，合入 PR head 并解决冲突，推送后按本 Skill 的平台文案规则创建中文人话的替代 PR/MR，正文关联原请求并说明冲突处理、实际纳入内容、验证与风险。替代请求合并前不关闭原请求。

默认用 merge 保留双方历史；只有仓库明确要求线性历史时才 rebase。禁止直接把未满足仓库策略的本地合并结果推到保护目标分支。两个模式遇到可修复的 required checks 或 review 反馈都继续修复；交付合并不切换为重复全量评审，产生新 head 后补受影响本地检查并等待该 SHA 的 required checks。对数据迁移、安全边界等高风险改动，要求最新 base、本地检查和 merge queue（若仓库启用）。

### 4. 冲突处理

按 checklist 理解并解决每个冲突。PR 处理模式验证冲突结果；交付合并模式只对冲突影响运行一次本地检查并复核 required checks、review 和平台闸门。漂移或推送失败时重新基于最新状态处理，不升级为强推。

### 5. 合并与验证

平台合并前按 checklist 完成本地前进预检：先把本地目标分支同步到当前远端 base；再检查未提交路径、PR 预计更新路径、Git 进行中状态、worktree 占用和分支 ahead/behind。未提交改动与目标更新不重叠且状态指纹未变化时，允许保留这些改动并在合并后原地 fast-forward；路径重叠、分叉、活跃并发写入或无法证明可安全同步时，停在平台合并前协调或处置。

预检通过后，通过支持 expected head SHA 的平台 API 或 merge queue 原子合并，记录最终 SHA，并确认平台状态、目标分支、required checks、review/保护策略和部署/迁移影响。若请求在本流程接手前已经合并，立即进入本地同步恢复；本地尚未包含该结果时不得把流程标记为完成。

### 6. 同步本地目标分支

平台确认合并成功后，立即获取权威 remote 的最新目标分支。目标分支通常是 `main`，但必须使用 PR/MR 的实际 base；若用户明确要求合入当前 `main`，则在平台合并前确认 base 就是 `main`，不得先合到其他 base 再私自二次合并。

保护所有现有工作区和本地提交，定位本地目标分支所在 worktree。目标分支已检出时，在合并前状态指纹未变化且本地 ref 是远端 ref 祖先的前提下执行 fast-forward-only；工作树不必为空，不重叠的未提交改动继续保留在更新后的目标分支之上，并以 Git 自身的覆盖检查作为最后一道保护。目标分支未被任何 worktree 检出时，使用绑定旧 SHA 的 CAS 更新把本地 ref 快进到远端 ref，不强行切走其他活跃分支。禁止绕过工作树直接移动一个已检出分支的 ref。

更新后必须验证本地目标分支与刚 fetch 的远端目标 ref SHA 一致，且包含平台返回的最终合并 SHA；远端分支随后又前进时，以本次 fetch 的最新远端 tip 为准并验证最终合并 SHA 仍可达。同步失败时继续处理真实原因；若出现预检后新增的重叠改动、分叉或活跃写入且无法自行安全协调，保留现场并明确请求所需决定，但整个合并任务仍是未完成状态，不得以“远端已合并、本地未同步”结束为成功交付。

### 7. 清理分支与现场

仅在合并成功，或本流程创建的现场已被明确废弃并由新现场完整取代后清理：

- 本流程创建及上游移交的完整任务现场交给 `$commit`，并提供所有权、活跃状态、交付组和指纹证据；主 agent 接管子 agent 现场，后续交付组仍需使用的资源保留到最终收口。
- 恢复已有 PR/MR 时，按 `$commit` checklist 用原任务/附件 metadata 与精确 repo、base/head SHA、branch/worktree 路径绑定原现场，显式接管并核对 owner 已释放、当前新增提交和 dirty 内容。归属未知或后续成果未交付时保留并报告，不因原 PR/MR 已合并而丢弃。
- 合并前记录精确 PR/MR head SHA；删除远端 head 前重新读取真实 ref，确认它仍等于该 head SHA，而不是最终 merge SHA，并确认它属于当前项目、不是默认/保护分支、没有其他开放 PR/MR 使用且没有明确活跃用途。
- 满足全部安全条件时必须删除同仓库远端 head，并在删除后重新读取平台 ref 验证；仓库未开启自动删除不是保留理由，改为显式删除。
- 用户明确要求保留、fork 分支、权限或归属不清、其他开放 PR/MR 仍引用、保护分支、活跃用途或 SHA 漂移时保留并报告。已确认缺少删除权限或没有带 expected SHA/lease 的安全删除路径属于未完成的清理阻塞，不得包装成正常保留；除此之外不得把“用户没单独要求删分支”作为保留理由。
- 若使用替代 PR/MR，在正文记录实际纳入的原 source head SHA，替代请求重新执行本地检查、required checks 与 review/平台闸门。合并前和关闭原请求前都重新检查原 head；只有它仍等于已纳入 SHA 时才关闭原请求。若它已前进，保留原请求处理新增 delta。
- 本流程创建但因 head/base 漂移而废弃的替代请求、分支和 worktree，可以在确认未被引用且内容已被新现场取代后关闭/删除，并留下替代关系。

完成或暂停前调用 `$commit` 的“远端已完成”模式，显式传递本任务资源清单与任务清理范围，只做本地盘点和安全清理，不再创建或合并 PR/MR；恢复该 PR/MR 必需的 AI 现场标记为活跃；用户、其他任务或归属不明现场保持原样，不以它们阻塞本任务收口。用户明确要求全仓清理时才另行传递全仓范围。该调用不得替代第 6 步的本地目标分支同步。

## 最终回复

必须包含：

- PR/MR URL、base/head 和调用入口；PR 处理模式给出评审结论和主要风险，交付合并模式说明上层验证上下文
- 本地验证、required checks、review 与平台策略结果
- 冲突文件、解决原则和冲突解决提交（如有）
- 合并方式、最终 SHA 和平台合并状态
- 本地目标分支、所在 worktree、同步前后 SHA、对应远端 ref，以及本地已包含远端合并结果的验证；本地未同步时必须明确整个合并任务尚未完成
- 使用的模式；交付合并时列出 head/base SHA、平台检查结果和跳过代码审核的上层流程依据
- 关联远端分支的删除或保留结论与安全证据
- `$commit` 返回的本地收口与全仓现场状态表，包括额外本地分支/worktree和真实远端开发分支的合并证据、新增提交/dirty 与处置理由；没有当前任务资源时也不省略该状态表
