# Reliability Observability

## 错误处理

- 业务错误和系统错误分开；不要用一个 500 装所有失败。
- 对用户返回稳定错误语义，对日志记录足够上下文。
- 跨层传递错误时保留分类和根因，只在系统边界翻译公开错误；不要每一层都“记录后再返回”制造重复日志。
- 外部依赖明确连接、读取和总时限；根据业务语义选择熔断或降级，不能无限等待。
- 重试只用于可重试错误，必须限制次数和总预算，并使用退避与抖动；写操作重试必须配合幂等。

## 日志与追踪

- 关键请求记录 requestId、userId、业务 id、耗时和结果。
- 写操作、权限失败、队列失败、外部调用失败必须可定位。
- 日志不要只写“失败了”；要包含失败阶段和关键上下文。
- 有 trace/metrics 体系时优先接入项目现有方案。
- metric label 禁止使用 userId、requestId 等无界值；日志可以记录定位所需标识，但要按项目策略脱敏并控制高基数索引。

## 监控与告警

- 后端改动涉及支付、订单、登录、队列、导入导出、第三方调用时，检查是否需要监控。
- 指标优先覆盖错误率、延迟、吞吐、队列堆积、重试次数和死信数量。
- 告警要能指向处理动作；没有行动意义的告警只是噪音。

## 容量与背压

- 性能或容量相关变更先明确可验收目标：延迟分位、吞吐、并发、队列 lag、数据规模和资源上限；记录基线，不能只说“更快”。
- 连接池、线程/worker、内部队列和下游并发要联合设限；达到上限时明确排队、拒绝、降速或暂停消费，禁止无界堆积把过载变成雪崩。
- 负载测试使用接近真实的请求比例、payload、数据基数、缓存冷热和持续时间，同时观察 CPU、内存/GC、连接池等待、查询次数和下游错误。
- 按风险注入下游超时、缓存不可用、数据库池饱和、队列堆积和 consumer 重启，验证不会形成重试风暴、级联故障、丢失或重复副作用，并能稳定恢复。
- 压测和故障测试设置逐级加压、停止条件和隔离环境；未经授权不能向生产或共享依赖制造流量与故障。
- 优化必须针对测得的瓶颈并比较前后结果；吞吐提升不能靠放大错误率、尾延迟、资源消耗或数据不一致换取。

## 配置与运行时

- 配置明确来源、默认值、作用域和格式；必需配置在启动时校验，缺失或非法时快速失败且不泄露密钥。
- 沿用项目健康检查；readiness 只在实例能安全接流量时通过，liveness 不把暂时性下游故障放大为重启风暴。
- 优雅停机先停止接收流量和新任务，再在有界时间内处理在途请求；队列消费者按语义确认、释放或重新投递消息。
- 连接池、worker 并发、请求体、批次和内部队列必须有上限，并与容量和背压策略一致，避免资源耗尽拖垮实例或下游。

## 一次性动作与重启安全

- 新增初始化、迁移、数据修复、回填、预热、通知或外部同步前，先明确执行语义：每进程、每次启动、每次部署、周期执行，还是按全局/租户/业务键只执行一次。命名为 `init`、`bootstrap` 或“临时任务”不能替代这个判断。
- 带持久化或外部副作用的全局一次动作，不得直接放在模块加载、应用启动钩子、容器 entrypoint、健康检查、leader 重新选举、请求首访或其他会因崩溃重启、滚动发布、扩缩容、热更新和平台重试而重复进入的位置。
- 优先把这类动作实现为版本化 migration、部署阶段 Job、显式管理命令或有持久化状态的后台任务；执行入口与在线服务生命周期分离，并让操作版本、作用域和业务幂等键可审计。不要用内存布尔值、进程锁或本地文件证明“已经执行过”。
- 执行环境本身可能重试时，使用数据库唯一约束、原子状态迁移、租约/分布式锁或项目已有调度能力防并发认领；动作本身仍按可重入、可恢复设计。只在副作用全部安全提交后记录完成，失败中断时能识别已完成步骤并继续或补偿。
- 每次启动执行仅适用于本来就属于实例生命周期且可安全重复的工作，例如注册进程内 handler、构建内存索引或校验配置。缓存预热、schema migration 等即使由启动流程触发，也必须有明确的重复执行语义、持久化版本记录和多实例并发保护，不能因为通常无害就默认安全。
- 至少覆盖连续两次启动、两个实例并发启动和执行中途失败后重试；断言目标副作用不会重复、完成记录不会提前写入、失败可恢复。发布与回滚时确认旧版本不会把已完成动作再次解释为待执行，并为卡住、失败和重复尝试提供可定位日志与人工恢复入口。

## 发布与回滚

- 数据结构和代码发布顺序要兼容；必要时走 expand-contract。
- 新逻辑高风险时考虑灰度、开关或兼容双写。
- 回滚前确认缓存、队列消息、migration 和外部副作用是否会留下状态。
