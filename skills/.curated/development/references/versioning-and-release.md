# Versioning and Release Identity

## 项目规则与默认格式

先沿用项目已公开的版本契约、生态工具和发布流水线。以下是尚未建立规则时的默认约定；普通开发不借统一格式改造既有版本体系。

- 新建可独立发布单元默认使用 SemVer：`MAJOR.MINOR.PATCH`，版本值与 tag 前缀、环境和构建身份分离；格式以生态解析器为准。
- 新实验性发布单元从 `0.1.0` 开始；对外契约准备稳定并愿意承担兼容承诺时发布 `1.0.0`。在 `0.y.z` 阶段，破坏兼容增加 `MINOR`，所有兼容变化增加 `PATCH`，避免每个项目自行解释 `0.x`。
- CalVer、平台专用版本或其他明确方案按实际需求选择，不为风格偏好换轨。统一旧项目时按下方迁移规则处理。

## 发布单元与权威来源

- 先识别发布单元：始终一起构建、部署和回滚的一个产品使用固定单版本；能被独立消费、部署或回滚的 monorepo 包使用独立版本。不要在没有发布工具支持时混用两种模式。
- 每个发布单元只保留一个可人工修改的权威版本源：优先使用生态主 manifest；没有合适 manifest 时使用仓库已有的 release 配置或根 `VERSION`。锁文件、生成代码、About 页面、响应 header 和构建产物从权威源生成或校验，不维护多份自由文本版本号。
- 单发布单元使用 Git tag `vX.Y.Z`；独立版本 monorepo 使用 `<package>@X.Y.Z`。manifest 不带 `v`，tag 才带固定前缀；不要混用 `release-1.2`、`v1.2.3-prod` 等样式。
- 把发布版本与构建身份分开：Git SHA、CI build number、构建时间和镜像 digest 用于追踪具体产物，不参与 SemVer 兼容级别。相同不可变产物在 dev、staging、prod 间晋级，不能因环境不同改版本。

## 确定版本增量

以同一发布单元的上一正式版本为基线，检查尚未发布的全部变化并采用最高级别；下表用于 `>=1.0.0`，`0.y.z` 严格使用上文“破坏性改 `MINOR`、兼容变化改 `PATCH`”的规则：

| 增量 | 条件 |
| --- | --- |
| 不变 | 尚不发布；仅改未交付的文档、测试或开发工具，且没有发布产物变化 |
| `PATCH` | 向后兼容的 bug、安全、性能、依赖或内部实现修复 |
| `MINOR` | 向后兼容的新功能、新 API、可选配置或已有能力扩展 |
| `MAJOR` | 删除/重命名公共能力、改变既有语义或默认行为，或要求消费者修改代码、配置、协议、数据文件或运维流程 |

- 版本判断面向消费者可观察契约，而不是 commit 类型、文件数量或代码行数；多个变化并存时取最高级别，不连续 bump 多次。
- 数据库内部 migration 不自动触发 `MAJOR`；只有升级后破坏外部兼容或要求消费者采取不兼容操作时才按破坏性变化处理。发布、迁移和回滚风险仍按数据规则独立评估。
- 普通开发提交不自动修改版本。只有用户要求版本变更/发布、项目明确采用每次交付 bump，或当前 release 流程规定由工具写入时才更新权威版本源。

## 预发布

- 没有既有约定时使用 `alpha.N`、`beta.N`、`rc.N` 表达开发验证、基本完整和候选发布；沿用发布工具的排序与晋级规则，正式版移除后缀。
- 先确定最终目标版本再创建预发布，例如从 `1.4.2` 开发兼容新功能时使用 `1.5.0-alpha.1`，不要发布 `1.4.3-alpha.1` 后临时改成 minor。
- `+build.metadata` 只用于追踪，不影响版本优先级；不要依靠它区分必须可排序或可升级的发布，也不要用 `-dev`、`-test`、`-prod` 表示部署环境。

## 独立版本空间

- API 路径中的 `/v1` 只表示需要长期并存的破坏性协议世代，不跟随每次应用发布递增。
- 数据库 migration 使用项目迁移框架的单调 ID/时间戳，不改成应用 SemVer，也不要把 migration 序号当产品版本。
- 移动端展示版本与平台构建编号分别遵循项目和商店规则。容器保留不可变版本/SHA 与 digest；`latest` 只能是便利别名，不能作为部署真相。

## 执行与迁移

1. 读取 `AGENTS.md`、manifest、release 配置、最近正式 tag 和发布流水线，找出发布单元、权威版本源及现有公开规则。
2. 比较上一正式版本到当前候选提交的全部未发布变化，按消费者影响得出唯一 bump；不能只看最后一个 commit，也不能猜一个“顺眼”的数字。
3. 使用生态自带的 version/release 工具修改权威源并同步必要生成文件；不手工搜索替换整个仓库，不创建 tag、不发布、不推送，除非当前用户请求或交付流程明确授权。
4. 验证版本能被生态工具解析、严格递增、tag 不冲突，构建产物和运行时版本来自同一权威源；发布说明覆盖自上一正式版以来的完整变化。缺少这些证据时不能声称已通过发布闸门。
5. 统一旧项目时，先盘点已发布 tag、制品、依赖方和自动化，选择不倒退且不碰撞的 SemVer 基线，记录一次性映射和切换点，再更新校验/发布流水线；永不重写或重新标记已经公开的版本。
