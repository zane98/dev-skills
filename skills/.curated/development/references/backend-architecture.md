# 后端架构与复杂度取舍

用于模块边界、核心业务流程、状态/条件分支复杂或新增架构机制的任务。架构复杂度须对应真实业务或运行约束，不能由现有目录、表和框架术语反推需求。

## 先建立简单基线

1. 用一个典型业务动作说明：谁对什么对象做什么、哪些条件必须满足、哪个事实会改变。列明身份、不变量、权威写入者与一致性边界。
2. 从项目已有模块和最少必要状态出发，写出直接调用、清晰条件判断、明确事务的可行方案；不要预设需要规则引擎、微服务、CQRS、事件溯源或多层通用仓储。
3. 标出简单方案确实无法满足的条件及证据，例如跨系统结果未知、并发争用、已测得的容量限制或真实存在的独立生命周期。可逆且不影响关键行为的未知用明确假设，不为猜测的未来需求升级架构。
4. 在有实质取舍时比较候选方案的正确性、读写成本、变化影响和恢复/维护成本，保留最少必要机制。简单方案已经满足约束时直接采用，无需固定数量的方案或设计文档。

## 删除不必要机制

| 设计对象 | 保留它需要的理由 |
| --- | --- |
| 新实体、状态或持久化字段 | 独立身份/生命周期、不可丢失的历史事实或明确一致性需要；纯展示和可可靠派生值优先投影 |
| 新分支或兼容路径 | 不同的真实业务规则或仍有调用方的兼容窗口；错误的状态归属先修正，不继续叠兜底 |
| 接口、策略、通用框架 | 已存在的变化/替换边界或稳定重复语义；不为一次调用包多层，也不强行合并相似但不同的业务 |
| 消息、队列、缓存或预计算 | 可说明的时延、容量、隔离或可靠性收益，以及明确所有者、失效/重试和恢复代价 |
| 服务或模块拆分 | 业务能力、数据所有权与变化边界清楚；拆开后不靠更多跨模块同步维持同一事实 |

重复存储或冗余读模型有时是合理选择，但必须说明权威源、更新机制、可接受滞后与重建方法。不要用“简化”取消金额守恒、权限隔离、幂等或失败恢复。

## 模块与业务逻辑

- 代码按业务能力和动作归属；领域规则集中在拥有该事实的模块，API 和 UI 消费其结果。service 按内聚动作或聚合边界组织，不把所有流程塞进万能 service。
- 将纯业务决策与 I/O 编排分开到足以读懂和验证的程度；正常路径直接可读，异常出口明确。有限规则用简单函数/判定表，只有组合复杂且事件驱动时才采用状态机等机制。
- 区分“业务本来复杂”和“表示方式制造的复杂”。先检查重复状态、双向同步、多个权威源和边界泄漏，再考虑拆文件或增加设计模式。
- 选择下一次最可能发生的业务变化，推演需要修改哪些位置；若同一规则散落到多个服务、SQL 和 UI，先收回规则所有权。
- 审查最终方案时说明删掉了什么、保留的复杂度解决什么。局部修复只处理受影响边界，不借审查扩大重构。
