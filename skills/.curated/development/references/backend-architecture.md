# Architecture Design

## 第一性原则

- 架构服务业务，不服务图纸；先理解业务动作、变化频率、数据边界和团队维护成本。
- 不用同一种标准评价所有项目；后台 CRUD、交易系统、内容系统、AI 流程、实时系统的压力点不同。
- 默认选择简单可改的结构；复杂架构必须能解释它解决了哪个真实问题。

## 设计顺序

1. 找业务核心：谁在什么条件下改变什么状态。
2. 找稳定点：哪些规则短期不会变，适合作为领域边界。
3. 找变化点：哪些流程、策略、第三方、展示口径最可能变。
4. 定模块归属：代码跟着业务能力走，不跟着技术名词乱飘。
5. 定数据边界：哪些数据必须强一致，哪些可以最终一致。
6. 定复杂度预算：先用项目已有模式；只有现有模式明显撑不住时再升级。

## 简洁与易修改

- 优先清晰分层和明确模块边界，不急着上微服务、CQRS、事件溯源、通用仓储等重装备。
- 对变化频繁的外部依赖、策略规则和通知渠道留接口；对稳定内部逻辑不要过度抽象。
- 一个模块应该有清楚的业务名字、输入输出和数据所有权。
- service 不要变成万能垃圾桶；按业务动作或聚合边界拆分。
- 目录结构能帮助定位代码即可，不为了“看起来高级”制造深层套娃。

## 判断问题

- 这个设计让当前需求更容易交付了吗？
- 下次最可能变化的地方在哪里？修改会影响几个模块？
- 数据一致性边界是否清楚？
- 是否引入了项目当前不需要维护的概念？
- 新人能否通过目录和命名理解业务流向？
