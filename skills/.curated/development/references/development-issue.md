# 开发问题与技术债务

仅将无法顺手完成的独立后续工作交给项目问题跟踪系统。已有登记授权才创建或更新平台记录，否则在回复中给出可提交草稿；不为登记后续项打断当前交付。

## 分流

按以下顺序判断：

1. 问题是否由本次改动引入，或影响本次正确性、安全、兼容性、数据一致性、验收与必要测试？是则纳入当前任务并修复，不创建 issue 代替交付。
2. 独立缺陷是否有证据、正确行为明确，且能在当前过程安全修复并验证？是则直接处理，必要时拆分提交；不因“独立”或“历史遗留”转成授权问题。
3. 需要另立产品目标、大规模重构、暂缺必要信息或外部条件，且不阻塞当前交付？才进入 issue 流程，继续完成当前任务。
4. 只是猜测、偏好或缺少证据的想法，不创建 issue；必要时在最终回复中说明观察和验证缺口。

用户明确限定只记录或不修复时照办。文件数、模块数和根因数量不决定是否询问；只有当前交付确实依赖无法自行确定的产品选择或未授权的外部动作时，才针对那个决定询问。

## 创建或复用 Issue

1. 确认仓库 remote、项目跟踪系统与模板；GitHub 优先使用 `gh` 或 API，其他平台使用其现有工具。
2. 用错误现象、模块名和关键术语搜索开放与近期关闭的 issue。已有等价项时复用并补充必要证据，不创建重复项。
3. 创建 issue，正文至少包含：背景与证据、影响、建议范围、验收条件、相关代码位置，以及与当前任务或 PR 的关系。根因或方案未验证时明确标为假设。
4. 只使用仓库已有且语义匹配的 label、assignee、project 或 milestone；没有把握时留空，不虚构分类。
5. 创建后重新读取 issue，确认 URL、编号、正文和状态；在当前计划或最终回复中引用链接。

不得在 issue 中泄露 secret、个人数据、内部凭据或不应公开的日志。公开仓库中的敏感证据应先脱敏；无法安全描述时停止创建并报告原因。

## 本地文档边界

- 默认不另建本地债务清单或向产品/架构文档追加问题流水；用户要求本地产物或项目已有权威 backlog 时沿用，不强制迁移到 GitHub。
- 开发计划只保留与当前交付相关的任务、阻塞和决策；后续项最多记录 issue 编号、标题与链接，不复制 issue 正文或维护第二套状态。
- 产品事实、长期架构决策和当前实施计划仍按各自文档协议维护；它们不是技术债务清单的替代品。
- 不因本协议批量删除仓库已有债务文档。当前任务明确迁移旧条目时，逐条去重并创建或关联 issue，确认远端记录成功后再删除对应本地条目。

目标平台不可用、认证或权限不足时保留可直接提交的草稿，说明未登记及原因；独立后续项不能因此阻塞已完成的当前任务。
