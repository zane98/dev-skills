# Cache And Queue

## 缓存设计

- **先找重复成本和事实源。** 沿实际读写链路区分数据库读取、外部调用与纯计算；优先复用输入未变的数据和结果，不只给最显眼的调用加缓存。命中路径不应为确认缓存是否可用又完整查库；先修复慢查询或错误模型，再判断缓存收益。
- **先定依赖与失效，再选过期时间。** 明确缓存对象、完整输入、账号/租户/权限作用域、影响它的写入入口，以及哪些操作必须读取权威数据。聚合结果同时依赖多个实体时，更新其中一个实体必须失效相关结果；单个实体版本不能冒充全部依赖版本。派生结果的 key 只纳入影响结果的输入；备注等无关变化不触发重算，但仍照常提交。
- **沿用统一机制。** 优先复用项目缓存层；缺少规范的 Go 项目参考 go-zero 的 cache-aside：读缓存，未命中再加载并回填；数据库写入成功且事务提交后删除受影响 key，下一次读取重建。key、回源、失效与错误处理集中维护，业务声明依赖，不各写一套 Get/Set；借鉴机制不等于迁移框架或引入新依赖。
- **依赖不变即可复用。** 固定坐标对的距离、固定版本配置及完整输入确定的纯计算可按输入或版本复用；可变资料不能只按对象 ID 永久保留。权益到期、规则生效等也是失效条件。TTL 可回收和兜底，不能代替本地可控写入的更新失效；外部数据没有变更通知时，按业务鲜度选择重查并说明边界。
- **覆盖写后竞态和恢复。** 核对后台、任务、批量写入等真实入口及事务回滚；处理删除失败、旧读取在失效后回填、跨实例和事件乱序。按已有机制选版本校验、条件回填或可靠再次失效，不默认加分布式锁。需要重启后仍可恢复时复用持久化任务/事件；进程内重试不等于持久化补偿，不因普通缓存一律新增 outbox。
- **明确一致性边界。** 展示/预估允许最终一致时说明收敛路径；授权、余额、库存扣减和交易冻结等按业务要求读取权威事实，事务未提交数据不进入共享缓存。组合缓存不能默认具有数据库一致快照语义，缓存值不能替代业务成功事实。
- **保护回源。** 同 key 并发未命中优先复用现有请求合并；单进程 singleflight 不提供跨实例锁或数据库与缓存的原子性。空值缓存、批量读取、限流和过期抖动按实际流量使用；区分未命中与缓存故障，后者不默认把全部流量转给数据库。
- **按风险验证。** 比较冷/热路径的 SQL、外部调用次数和耗时，验证依赖变更失效、作用域隔离，以及实际涉及的回滚、并发回填、删除失败恢复和业务到期。不能以写入 Redis 成功或命中率代替一致性证据。局部、不可变的简单复用沿用现有 memo/容器即可，不扩成分布式缓存工程。

参考 go-zero 的[读取与失效](https://go-zero.dev/components/cache/redis-cache/)、[数据库封装](https://github.com/zeromicro/go-zero/blob/master/core/stores/sqlc/cachedsql.go)与[清理重试](https://github.com/zeromicro/go-zero/blob/master/core/stores/cache/cleaner.go)。落地时核对实际版本：标准实体缓存不自动解决列表、跨实体派生结果或事务一致性。

## 队列任务

- 明确 broker 的投递语义；没有可验证保证时按 at-least-once 设计，不能口头许诺 exactly-once。
- 队列消息必须有业务唯一键或幂等键。
- handler 可重复执行；重复消费不能造成重复扣款、重复发券、重复通知等副作用。
- 只在业务状态和必要副作用安全落地后 ack；数据库写入与发消息必须一致时优先使用项目已有 outbox/事务消息方案，否则明确失败恢复与对账路径。
- 只有业务需要时才保证顺序；用稳定 partition key、sequence/version 处理同一业务键的重复和乱序，不能假设全局有序。
- 消息 schema 要有兼容策略：优先新增可选字段，消费者容忍未知字段，明确 producer/consumer 发布顺序和旧消息存量处理。
- 定义重试策略、最大次数、死信处理和人工补偿入口。
- 消息体只放必要数据；大对象放存储或数据库，消息里放引用。
- 任务日志必须包含 taskId/messageId、业务 id、重试次数和失败原因。

## 后台任务

- 定时任务要防并发重入；多实例部署时使用锁或调度器能力。
- 批处理要分片、分页或游标推进，避免一次扫完整库。
- 可恢复任务要保存进度；失败后能从安全位置继续。
- 长任务响应取消和优雅停机；有 lease/visibility timeout 时按项目能力续租，超时重投仍必须幂等。
