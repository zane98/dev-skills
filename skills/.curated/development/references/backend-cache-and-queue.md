# Cache And Queue

## 缓存边界

- 使用缓存前先说明目的：降延迟、抗流量、减少重复计算，还是保护下游。
- key 必须稳定、可读、包含业务作用域；避免不同用户或权限数据串缓存。
- TTL、主动失效和被动过期策略要明确；批量写入或预热时避免大量 key 同时过期。
- 缓存穿透要在参数校验、短期空值缓存或项目已有过滤方案中按风险选择，不能让不存在的数据无限打到数据库。
- 热点 key 或缓存击穿要按项目能力选择请求合并、互斥重建、提前刷新，或在业务允许时短期返回旧值，避免过期瞬间把流量同时压向下游。
- 缓存雪崩要考虑 TTL 抖动、分批预热、限流和降级；缓存不可用时必须保护数据库，不能无上限全部回源。
- 缓存一致性要说人话：允许旧多久、什么场景必须强一致、失败时怎么降级。
- 不要用缓存隐藏慢查询或错误数据模型；缓存是加速器，不是遮羞布。

## 队列任务

- 明确 broker 的投递语义；没有可验证保证时按 at-least-once 设计，不能口头许诺 exactly-once。
- 队列消息必须有业务唯一键或幂等键。
- handler 可重复执行；重复消费不能造成重复扣款、重复发券、重复通知等副作用。
- 只在业务状态和必要副作用安全落地后 ack；数据库写入与发消息必须一致时优先使用项目已有 outbox/事务消息方案，否则明确失败恢复与对账路径。
- 只有业务需要时才保证顺序；用稳定 partition key、sequence/version 处理同一业务键的重复和乱序，不能假设全局有序。
- 消息 schema 要有兼容策略：优先新增可选字段，消费者容忍未知字段，明确 producer/consumer 发布顺序和旧消息存量处理。
- 定义重试策略、最大次数、死信处理和人工补偿入口。
- 消息体只放必要数据；大对象放存储或数据库，消息里放引用。
- 任务日志必须包含 taskId/messageId、业务 id、重试次数和失败原因。

## 后台任务

- 定时任务要防并发重入；多实例部署时使用锁或调度器能力。
- 批处理要分片、分页或游标推进，避免一次扫完整库。
- 可恢复任务要保存进度；失败后能从安全位置继续。
- 长任务响应取消和优雅停机；有 lease/visibility timeout 时按项目能力续租，超时重投仍必须幂等。
