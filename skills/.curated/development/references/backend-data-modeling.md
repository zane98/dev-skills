# Data Modeling

## 业务建模前置

- 先从业务场景识别参与者、租户/主体、业务对象、动作、生命周期和并发来源，再决定表、字段与关系；页面表单和 API payload 只是视图，不是数据模型本身。
- 明确每个业务事实的权威来源、稳定身份和不变量：什么必须唯一，在哪个范围和时间内唯一，什么允许重复，重复是新事实、重试还是冲突。不要把自增 ID、展示名或当前页面字段误当业务身份。
- 在设计前走查创建、更新、批量导入、消息重放、请求重试、并发写入、失效、软/硬删除、恢复、租户迁移和历史数据回填；只覆盖“首次正常创建”的模型通常不完整。
- 区分实体身份、幂等身份和展示身份。实体唯一键回答“是不是同一个对象”，幂等键回答“是不是同一次动作”，展示字段只服务用户识别；三者不要混用。
- 先写出数据规模、增长速度、保留周期和主要读写路径的合理假设；能从 schema、代码、日志或产品文档取证时直接取证，关键假设会改变约束或架构时再请求决策。

## 数据变更

- 新增字段必须明确默认值、nullable、历史数据填充和读写兼容策略。
- 删除或重命名字段先确认调用方、报表、任务、导入导出和历史数据影响。
- migration 遵循项目迁移框架和版本记录；评估事务支持、中断、部分执行和重试，不能把执行失败当作数据回滚。
- 生产大表变更要评估锁表、执行时长、分批回填、监控，以及代码与 schema 的兼容发布顺序。
- 破坏性或不可逆变更提前明确备份、expand-contract、回滚或前向修复路径，不能假装数据一定可逆。

## 映射正确性

- 对齐 schema、列名/alias、持久化 model、类型和 DTO 映射；不要依赖 ORM 猜测关键字段。
- 明确区分字段缺失、数据库 NULL、语言零值和业务默认值；nullable 字段使用项目约定的指针或 nullable 类型。
- 把“读取后修改再保存”也视为映射边界：检查 nullable 值经过语言模型和 ORM 往返后是否仍为 NULL；完整查询得到的 model 也可能因非 nullable 语言类型丢失 NULL 语义。
- raw SQL 的返回列、顺序和目标类型必须匹配并检查迭代错误；状态流转、局部修改和 ORM 部分查询只更新当前动作拥有的明确字段，避免全量保存把 NULL、未加载字段、数据库默认值或生成值改写成语言零值。
- 区分字段未提供、语言空值、SQL NULL、JSON `null`、`{}` 和 `[]`，按字段契约明确序列化与默认值。不得用全局 hook 把缺失值改成具体空对象/数组来绕过约束；Go/ORM 的具体往返检查见 [Go 数据映射](backend-golang.md)。
- PostgreSQL `NOT VALID` 约束只跳过存量全表校验，仍会约束新写入；nullable 外键被 ORM 从 NULL 改写成空值时会在普通更新中触发约束错误，不能把它当成无关历史脏数据。
- 映射敏感变更先记录真实数据库往返需求；使用项目真实数据库引擎、driver 和 schema 检查，集成测试直接断言 `IS NULL`、约束与数据库往返结果。mock 或只看语言零值无法证明 NULL、类型转换和 ORM tag 正确。

## 金额与时间语义

- 金额使用项目统一 decimal 类型或最小货币单位整数，禁止 binary float；同时保存/传输明确币种，数据库、领域模型和 API 的精度必须一致。
- 把 scale、舍入模式和舍入时点写成业务规则；税费、折扣、分摊和汇总不能在不同层各自随手 round。
- 汇率必须记录来源、基准/报价币种、有效时间或版本和精度；历史交易保留当时使用的汇率与结果，不能按最新汇率静默重算。
- 区分 instant、带时区本地时间、纯日期和业务周期；事件时间通常保存 UTC instant，预约/营业时间还要保存业务时区，不能把本地日期粗暴当 UTC 零点。
- 周期任务和日历规则要处理 DST 的重复/不存在时间；只保存固定 offset 不足以表达未来时区规则，时区标识沿用项目和平台标准。
- 业务判断通过项目 clock/time provider 获取“现在”；测试固定或推进时钟。超时和耗时测量使用单调时钟能力，避免系统时间回拨破坏判断。
- 金额和时间变更使用真实 driver/schema 检查序列化与数据库往返，覆盖精度、舍入、时区、DST 和日期边界。

## 表、唯一性与索引

- 表达业务事实，不为了某个页面临时堆字段；避免无边界 JSON 大字段，只有 schema 不稳定且查询需求弱时才用。
- 为每条唯一规则明确范围：全局、租户/组织、用户/主体、父资源、类型、状态、时间窗口或仅有效记录。把参与范围的字段放进数据库唯一约束，不用模糊的单列唯一代替业务语义。
- 明确 NULL、空字符串、大小写、前后空白、Unicode、排序规则和标准化后的相等语义；需要标准化时保存规范值或使用目标数据库可靠支持的表达式索引，并让读写路径采用同一规则。
- 软删除、有效期和状态会改变唯一性时，优先使用目标数据库支持的部分唯一索引、显式有效身份或等价可靠方案；先定义删除后能否复用、恢复冲突如何处理，不能默认把 `deleted_at` 塞进唯一键就算完成。
- 唯一约束必须落库以兜住并发；应用层查询可用于友好提示，但写入仍要捕获约束冲突并映射为稳定业务错误。不要依赖“先查不存在再插入”。
- 幂等写入使用稳定、可限定作用域的幂等键或业务唯一键，并定义相同键同参数、相同键不同参数、处理中、成功和失败重试的结果；唯一约束只是原子闸门，不自动等于完整幂等语义。
- 从真实查询形状设计索引：等值过滤、范围过滤、关联、排序、分页和选择性共同决定列及顺序；同时检查外键关联、清理任务和状态扫描，不能只优化当前页面的一条查询。
- 组合索引按目标数据库的最左前缀、排序和覆盖能力验证；低选择性单列索引、重复前缀索引和被现有索引覆盖的索引通常只增加写放大。新增前盘点现有主键、唯一约束和索引。
- 评估索引占用、写放大、锁、在线创建能力和 migration 时间；大表索引要有兼容发布、监控、中断重试和回滚/前向修复路径。
- 使用与生产一致的数据库引擎、schema 和代表性数据检查约束冲突与查询计划，覆盖重复、并发、跨租户、NULL/标准化、软删除/恢复和历史脏数据；缺少证据时不能仅凭 ORM 声明或“建了索引”判断正确。

## 事务与一致性

- 一个业务动作涉及多表写入时，先确定事务边界。
- 事务内所有读写使用同一 transaction context/connection；事务尽量短，不把普通重复查询变成长锁和额外竞争。
- 同一事务内同一业务记录原则上加载一次并传递结果；只有锁语义、隔离级别、数据库生成值或并发正确性要求时才重新查询，并说明原因。
- 外部调用不要随意放进数据库事务；需要补偿或 outbox 时明确。
- 并发更新考虑乐观锁、悲观锁、唯一约束或幂等键。
- 金额、库存、额度、状态流转等不能只靠前端或缓存判断。

## 查询设计与性能

- 先定义结果粒度：一行代表哪个业务对象、需要哪些事实、过滤/排序依据、租户/权限边界、分页与总数语义。不要让页面展示结构逼出全域查询。
- 对复杂查询比较有意义的替代方案：数据库内集合运算，或先取得正确的主结果集、再按本页 ID 固定次数批量加载关联。查询次数、扫描/返回行数、往返、内存、锁与可维护性共同决定选择；不以单条 SQL 为目标，也不机械限制 SQL 行数、CTE 或 JOIN 数量。
- 用 query log、APM 或测试计数器检查查询次数与结果规模的关系，避免循环、序列化和 ORM hook 中隐藏 N+1；批量方案的往返次数不应随每条结果线性增长。
- 按关联基数选择 join、EXISTS、先聚合再关联或批量读取。两个独立一对多直接相连可能使计数/金额重复；先在各自业务粒度聚合，不能靠最终 DISTINCT 掩盖含义错误。
- 影响资格、筛选、排序和权限的条件必须在分页之前处理；只有不影响主结果集的展示关联才适合分页后补齐。拆查询要说明快照一致性、并发变化和有界批次，避免内存过滤或排序改变全局分页结果。
- SQL 负责适合数据库的过滤、连接和聚合；领域状态转换与副作用由明确业务所有者负责。重复 CASE、关联子查询、跨域状态拼装是审查信号，不是绝对禁令；CTE 只改可读性时不能宣称降低执行成本。
- 用目标数据库与代表性数据检查查询计划、实际扫描/返回量、耗时、排序和索引；考虑数据倾斜和目标并发。可能执行写入或产生负载的分析命令只在适当隔离和授权下运行。
- 优化先修正语义、过滤、字段与访问路径；必要时比较索引、批量和聚合，再考虑缓存或读模型，并计入失效、更新和重建成本。报表类查询确需复杂集合运算且代价可接受时可以保留。
- 大列表、导出与后台任务按真实规模使用有界批次、流式或异步处理；结果总数明确有界且规模很小时不强制分页。
