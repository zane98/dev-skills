# Design Token Governance

实现视觉、映射 Figma 或新增/修改 design token 时，使用本参考。

## 模型与优先级

- 基础 token 定义原始 scale，如 palette、spacing、typography、radius、shadow、motion 和 breakpoint。
- 语义 token 表达用途，如 `text-primary`、`surface-muted`、`border-danger`；业务代码优先使用这一层。
- 组件 token 只服务稳定组件和状态，如按钮背景、弹窗阴影；不要为单个页面建立组件 token。
- 使用顺序：设计系统组件的 props/variant > 组件/语义 token > 基础 token > 允许的硬编码例外。
- 一个项目保持一个视觉事实源；不要在 CSS variables、Tailwind theme 和 TS map 中复制互不联动的值。

Token 可覆盖颜色、字体、间距、稳定尺寸、圆角、阴影/层级、断点、动效、z-index、透明度和 focus ring。不要存业务文案、URL、接口字段、产品枚举、一次性偏移或组件内部计算值。

## 查找与映射

1. 搜索 token/theme 文件、CSS variables、Tailwind 配置、设计系统包和 Figma variables/styles。
2. 查看已有组件和相邻页面如何消费 token，确认真实命名、主题和模式。
3. 按语义映射颜色和状态，按 scale 映射字体、间距、圆角、阴影和动效；不要只挑肉眼最接近的原始值。
4. 同时检查 light/dark、品牌主题、响应式和交互状态，不只实现当前截图。
5. 现有 token 无法表达时，先判断是设计冲突、系统缺口还是一次性例外。

## 字体、间距与页面模式

- 沿用主题定义的字体族与中文/西文回退链，核对实际加载和缺字回退；不逐页引入外部字体或另设 font-family。标题、正文、辅助信息等复用项目已有的字号/行高/字重语义组合，差异用于层级；不擅自换成另一套通用数值。
- 间距使用已有档位，并按同组内部、组间、区块间关系表达分组；同类密度复用组件 size/variant。不要只把零散值四舍五入到 scale，却保留混乱分组，也不强迫不同任务使用同一密度。
- 同类列表、详情、表单沿用已有 Layout、页面模式和样板；必要变化先说明任务差异，不在各页自由发明壳层与操作位置。缺少系统时从一个真实页面所需的最小规则开始，验证后再提炼确有复用的组件/布局，不先造完整库或更换品牌/技术栈。

## Figma 输入

Figma 链接、文件、节点或“按 Figma 还原”要求由 `$figma-design` 处理。它负责节点取证和属性映射；读取设计证据与运行态验收按执行边界区分，本参考只继续负责 token 的使用与治理。

## 治理决策

| 情况 | 动作 |
| --- | --- |
| 已有组件或语义 token 能表达 | 直接复用 |
| 同一稳定视觉语义在多个位置出现 | 新增或完善语义/组件 token |
| scale 缺口或可访问性问题影响多处 | 调整 scale/token，并覆盖受影响点 |
| 品牌色、字体体系、全局 scale、默认组件视觉或公共布局模式变化 | 提出具体方案、适用范围和回归范围；尚未授权且需要设计取舍时取得确认后修改 |
| 单页一次性值、临时实验、仅差 1-2px | 不新增 token |
| Figma 与系统冲突且影响品牌、层级或可访问性 | 提出 token 治理方案；不要大面积硬编码 |

新增字体、视觉样式、组件或布局前，简述现有能力为何不足、复用/组合为何不能解决，以及适用范围；已有明确授权或既定规范可直接落实，不因局部修复强制设计审批。语义和组件 token 按用途命名；基础 palette/spacing scale 可以用数值。避免把一次性页面位置包装成全局语义，不因命名偏好重命名现有稳定体系。

## 变更闭环

- 同步 token 定义、导出和实际消费者；多主题 token 必须补齐各主题值或明确继承链。
- 修改全局 token 前搜索全部使用点；重命名或废弃时提供兼容别名或一次性迁移，不留下两套长期真相。
- 项目已有 token 文档、Storybook、视觉快照或主题测试时同步更新；没有时不要为单次改动另建文档体系。
- 验证对比度、focus 可见性、主题切换、响应式和关键组件状态。

## 硬编码例外

- 布局数学：百分比、`fr`、`calc(...)`、aspect ratio。
- 资产固有尺寸、第三方 API 或目标平台强制值。
- 只在单处成立且没有稳定语义的实现值。
- 项目尚无 token 系统时，只为当前真实复用建立最小 seed，不顺手设计完整宇宙。

例外在现有约定、代码注释或本次交付中显式记录位置、理由和适用范围；数学/平台值可按类别说明，临时实验写明移除条件，不为此另建文档体系。能映射 token 的值收回系统。

## 可执行检查与人工判断

- 先查并运行项目已有的 lint、样式规则、token 检查脚本或 CI；明确命令、覆盖文件与已放行例外，不能只写“遵守设计系统”。缺少工具时先审查本次变更，可用 `rg` 定位候选后核对上下文；非必要不装依赖、不造庞大扫描器。
- 扫描本次新增/修改的任意字体、颜色、spacing 值（含 CSS/JS、工具类方括号值和绕过 token 的常量）、外部字体引入（`@font-face`、`@import`、字体链接/依赖）与内联 style；兼看圆角、阴影、时长等原始值。已有 style 机制、布局计算和批准例外按语义判断，不机械禁止所有内联样式，也不顺手治理整个历史仓库。
- 文本扫描有漏报/误报；规则合规只能支持一致性，不能证明层级、密度、留白或审美好。审美学习与运行验收见 [审美校准与验收](frontend-ui-quality.md) 和 [前端核心](frontend-core.md)。
