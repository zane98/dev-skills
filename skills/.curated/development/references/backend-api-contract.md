# API Contract

## 契约先行

- 明确调用方、业务动作、权限边界和数据所有者。
- 请求参数写清类型、必填、默认值、枚举、范围、排序和分页。
- 响应结构稳定：不要把数据库字段原样裸奔给前端。
- 错误语义统一：区分参数错误、未登录、无权限、资源不存在、冲突、限流和系统错误。
- 写接口考虑幂等：创建、支付、提交、回调、导入、队列触发尤其要防重复。
- 对外或跨端接口考虑版本兼容；删除字段、改字段语义、改错误码都算破坏性变更。

## 实现检查

- route/controller/handler 只做协议转换、鉴权入口和参数校验；业务事实放 service。
- service 负责业务规则、事务边界和领域错误。
- repository/dao 只处理持久化细节，不偷塞业务判断。
- DTO/VO/schema 与内部 model 分离；必要时增加 mapper，避免泄露内部结构。
- 前端页面需要什么就提供什么，但不要把无关大对象一股脑丢出去。

## 错误契约

- service 返回可分类的领域错误并保留底层原因；只在 controller/handler/统一中间件把错误映射为传输协议。
- 在一个 API 边界统一映射 HTTP status、业务 code 和安全的公开 message，三者必须表达同一失败语义。
- 参数、认证、权限、资源不存在、冲突和限流等已知错误按契约返回，不能全部掉进 500；下游错误也不能原样透传状态和内部消息。
- 不得把失败误写为成功；既有协议若使用 200 + 业务 code，保持兼容但必须让 code/message 真实表达失败，协议迁移另行处理。
- 只有未分类的异常才返回通用 500；响应携带 requestId，服务端记录完整错误链，不能泄露 SQL、路径、堆栈或内部依赖信息。
- 为每类领域错误写映射测试，断言前端实际收到的 status/code/message，而不只断言 service 返回了 error。

## 分页与查询

- 列表接口默认分页；明确 `page/pageSize` 或 cursor 方案。
- 排序字段白名单，禁止直接拼接任意字段。
- 搜索条件要能落到索引或可接受的查询计划。
- 聚合统计接口和明细列表接口分开，除非业务确实要求同屏同源。
