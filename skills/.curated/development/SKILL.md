# Development

从用户要达成的结果、权威事实和真实约束出发，选择最简单的正确实现，并完成当前已授权的工作。

## 工作边界

- 用户明确指令优先于 skill 默认流程，并服从更高层要求。开发、测试、提交与合并是连续执行链：默认直接修复过程中发现的代码、测试、构建、配置和本地环境问题，完成必要验证后继续原流程；切换 skill 或阶段不重置已有授权。只审计、只给方案、只测试不改代码、不要测试等明确限制照办。
- 按既定契约判断正确行为，自行决定工程方案。跨文件、跨模块、历史遗留、第二个根因或需调整测试都不单独构成询问理由；可确定并安全修复的附带缺陷顺手处理，按需拆分提交并说明。只在无法从现有事实确定会改变业务结果的选择，或具体动作缺少不可替代的权限时询问；先完成不依赖该决定的工作并准备可审阅结果。
- 写入前核对涉及路径的现有 diff、分支和所有者，保护用户 WIP；同一文件保持唯一写入者。未知归属只暂停相关写入，不冻结无关工作。命令、字段与运行状态以当前仓库和工具结果为据。
- 优先复用当前安全 checkout 或本任务已有 worktree；新建隔离现场必须有具体冲突或运行隔离依据。涉及 branch/worktree 的创建、接管、交接或收尾时读 [开发现场生命周期](references/worktree-lifecycle.md)，由主 agent 负责本任务及子 agent 现场的完整去向。
- 实现授权不自动扩大到 Git 交付、部署、生产数据、真实外部副作用或对外通知；已明确授权的完整流程按原范围继续。边界不清、验证受阻或长任务交接时读 [执行边界](references/execution-boundaries.md)。

## 设计与执行

1. **理解受影响行为。** 明确用户需要的结果、权威事实与不可破坏的约束，沿入口、事实生产方和必要消费方核对实际行为。新增产品行为读 [产品与交互](references/product-and-interaction.md)；bug 按下方原则定位，契约与根因已明确时直接修复。
2. **先选直接实现。** 优先复用现有能力完成当前行为。新增抽象、状态、存储或队列前，先指出直接实现无法满足的具体约束；“以后可能复用”和假想异常不足以增加机制。复杂度按本次变化判断，不因所在模块涉及支付、权限或异步就整套升级；这些领域已有的正确性约束仍须保留。文件长度不作为强制拆分阈值；确有跨层复杂状态时再读 [状态建模](references/logic-and-state-modeling.md)。
3. **推进到完成。** 按真实依赖实现事实生产方、高风险边界和消费方。复杂多步实施使用 $development-plan；小改动直接做。发现问题先定位并修复，只有无法顺手完成的独立后续工作才按 [Issue 分流](references/development-issue.md) 处理。用户中途补充要求时更新相关假设，保留仍有效的工作。

独立搜索和读取可批量并行。有可独立完成且能缩短关键路径的子任务、运行环境允许时，使用少量子 agent，交代目标、输入、写入范围和完成条件；主 agent 保持有用工作并负责集成。不为微小改动委派，不并行修改共享契约，不用新建用户任务代替子 agent。复杂调度由 $development-plan 负责。

## Bug 修复：从第一性原理出发

- **先核对前提。** 从预期结果、事实所有权和约束推导应有行为，区分既定契约与实现假设。现有代码、测试和历史补丁不能自行证明设计正确；用户提供的原因猜测也应作为假设核对，不为迁就错误实现改写业务规则。
- **用证据定位因果。** 获取最小复现或已有失败证据，追到最早违反契约的责任边界，说明“错误前提/机制 → 触发条件 → 可观察故障”。有竞争解释时选择能区分它们的检查，不靠反复试改碰运气；无法复现时保留不确定性，补充可做的静态分析或诊断，不把猜测称为已定位。
- **在根因所在层修复。** 最小正确修复以消除错误机制为准，不以改动行数最少为准。若事实源、模型、职责或流程本身有误，在授权范围内纠正，并调整必要消费方、移除本次修复已替代的补丁；避免在下游继续叠加特判、重复状态、吞错或默认值来掩盖上游错误。
- **反证出现就重审方向。** 修复无效、同类问题复发，或必须不断增加例外才能维持方案时，暂停沿用该假设，核对新证据和约束；撤掉本任务中已证伪的尝试后重新选择方案，保留他人 WIP。不因已经投入工作而维护错误路线。
- **修正范围与问题相称。** 局部实现错误直接局部修复，不借第一性原理扩大成全盘重写。有真实兼容性、外部故障或恢复约束的重试、防御和适配可以保留，但须说明它们解决的具体约束。确需临时止血时，明确缓解范围、未修根因与后续修复条件，不宣称根治；执行仍遵守工作边界。

## 验证与收尾

- 验证改变的行为与不变量。bug 检查应能在修复前暴露错误机制、修复后证明契约恢复，并按风险覆盖同根因的必要路径；一次表象消失不等于根因消除。低影响文案/样式先检查 diff 和必要显示；逻辑变化运行定向检查，缺少有效覆盖且风险值得时补回归测试。资金、权限、迁移和并发关注正常、拒绝、失败与恢复；不写只复述实现的测试。
- 完成项目适用的必需检查。检查通过后，只有新改动、失败或未解决疑点才扩大或重跑；环境、fixture、时序问题先定位，不能靠修改业务契约把测试调绿。
- UI 改动按需要取得受影响状态的运行证据；环境不可用时完成可做的检查并说明缺口。mock/截图、数据库回读、真实认证与外部结果各证明自身范围，不能互相冒充。
- 检查最终 diff，按需同步权威文档。简洁报告结果、关键原因、实际验证及剩余缺口；开发、Git、部署和外部结果分别表述，不要求固定长篇模板。检查流水不进入开发计划。
- 结束、暂停或交接前按现场生命周期收口；完成开发不等于完成合并。涉及任务分支/worktree 时报告明确合并状态、已清理项及保留理由；没有 Git 交付授权时保留唯一未交付成果，不借清理自动提交或合并。

维护本技能时，使用 [行为回归案例](evaluations/behavior.json) 核对决策与副作用，隐藏判定字段后再做独立回放。
