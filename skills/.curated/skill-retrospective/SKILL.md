# Skill Retrospective

把重复失败转成可验证的规则改进，避免用一次偶发问题污染长期指令。

## 流程

1. **确认授权**：只要求分析、总结或建议时不得改文件；明确要求更新、优化或沉淀时才实施修改。
2. **收集证据**：读取原始请求、预期与实际结果、错误或 diff、历次尝试、用户反馈、实际调用的 skill/tool 与副作用，以及当时生效的 skills、`AGENTS.md` 和环境信息；证据不足就说明缺口。
3. **定位根因**：选择最小充分归属：
   - 当前实现错误：修复当前任务，不改长期规则。
   - 项目特有且稳定的约定：更新作用域最窄的 `AGENTS.md` 或既有项目文档。
   - 工具、网络、权限或外部服务偶发异常：记录条件和恢复方式，不改 skill。
   - skill 的触发、流程、知识或冲突缺陷：更新对应 skill。
4. **检查门槛**：仅当存在两个同类实例，或一个稳定复现、影响明确且规则缺口确定的实例，并且用户已授权时，才修改长期规则。
5. **最小修改**：写出“缺陷 X 导致决策 Y；改动 Z 应使条件 C 下产生 W”，然后叠加 `$skill-creator` 修改最窄所有者。
6. **回归验证**：运行 `scripts/validate_skill_suite.py` 的结构检查，回放原失败案例，并用至少一个反例确认不会误触发；复杂或高影响改动再用不泄漏预期答案的新鲜上下文独立验证。

## 规则预算

- 把 Skill 修改当成重构，不当成追加日志。新增规则前先指出它替代、合并或删除了什么；确需净新增时说明现有规则为何无法覆盖。
- `description` 只负责触发与排除范围；`SKILL.md` 只保留稳定工作流、关键决策、停止条件和资源路由。案例、领域知识与长清单下沉到按需 reference，重复操作变成脚本或评测用例。
- 从失败中提炼可迁移的不变量，不保存事故表象。除安全、权限、数据损失和不可逆操作外，优先写带适用条件和例外的判断规则，避免绝对禁令。
- 修改前后比较字符数/行数、重复规则、绝对词和跨 Skill 调用；长段落不能借行数少伪装精简。增长本身不是错误，但每段新增内容都必须降低明确风险，且不能复制其他 Skill 已拥有的流程。
- 当入口体量明显增长、同一决策散落三处，或 pre-flight 清单持续增长时，先重组或删除再增加规则；不能用更多提示词掩盖路由、工具或实现问题。

## 修改归属

- 触发不准：修改 frontmatter `description`。
- 步骤、顺序或停止条件缺失：修改 `SKILL.md` 正文。
- 重复且需要确定性的操作：使用 `scripts/` 并实际测试。
- 详细领域知识：放入 `references/`，正文只保留读取条件。
- 多个 skill 重复或冲突：按适用范围保留唯一、最窄的规则所有者。

## 开发 Skill 协同

| Skill | 唯一所有权 |
| --- | --- |
| `development` | 统一开发流程，以及前端、后端和语言领域 reference 路由 |
| `development-plan` | 实现任务拆分、依赖和进度；生产执行归部署/Runbook |
| `resolve-issue` | Issue 证据、实现入口和交付编排 |
| `merge-pr` | PR/MR 评审、冲突、远端合并和关联分支 |
| `commit` | 本地提交与已确认 AI 现场的收口 |
| `aliyun-deploy` | 阿里云目标环境部署、排障和回滚 |
| `figma-design` | Figma Desktop MCP 取证、设计到代码映射与视觉验收 |
| `skill-retrospective` | 重复失败归因与整套 Skill 的最小演进 |

- 规则只写在最窄所有者；调用方只声明何时调用、传递什么状态、复用什么结果，不复制被调用方流程。
- Skill 串联不能扩大用户授权；实现、提交、远端合并、生产部署分别判断权限。
- 修改调用关系时检查正向路径、相邻 Skill 反例、停止边界和最终状态，避免局部优化破坏完整交付。

## 护栏

- 不把项目事实写进通用 skill，不把个人偏好包装成普遍规律。
- 不因单次失败新增绝对禁令，不用堆叠规则掩盖根因。
- 不把前一次任务、配色、组件、命令或文件名当作下一次任务的默认上下文；需要轮换或跨任务记忆的偏好不写进通用 Skill。
- 修改前确认每个 skill 的权威来源与安装位置，读取差异并保留已有改动。已映射源码只同步核对过的文件，独立技能可在原位置维护；不整目录覆盖或擅自编辑受插件管理的缓存。同步后比对实际内容。
- skill 触发语义变化时同步 `agents/openai.yaml`；不创建 README、变更日志或复盘档案。

## 半自动评测

- 先运行 `python3 scripts/validate_skill_suite.py --skills-root <skills-root> --cases evaluations/core-routing.json`。它自动检查 skill 元数据、UI metadata、相对引用和案例格式；它不声称能判断模型实际路由是否正确。源码目录只包含部分个人技能时，可用 --catalog-root <installed-root> 解析其余案例技能名；该参数不会验证额外目录中的文件。
- 领域案例由对应 skill 维护，例如 [计划完成口径](../development-plan/evaluations/completion-routing.json)。对本次改动涉及的专属案例再运行同一检查，不把相同案例复制到通用 suite。
- 对触发和决策语义，从 `evaluations/core-routing.json` 提取 prompt 与原始 context 给新鲜上下文，隐藏 expected/required/forbidden 字段和此前诊断。检查实际方案、工具动作与副作用；按行为约束判定，不能只匹配“第一性原理”等词。设计规则要包含允许必要复杂度的反例，权限规则要覆盖相邻入口的授权继承。
- 自动化只负责发现结构问题和收集可比较证据。没有用户授权、没有足够重复证据，或语义评测未通过时，禁止自动修改任何 skill。

## 输出

简洁报告问题、证据、根因、修改决策、目标文件、验证结果和剩余风险。不要承诺“以后不会再犯”，只说明已覆盖的失败路径。
