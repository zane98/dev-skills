# Skill Retrospective

把重复失败转成可验证的规则改进，避免用一次偶发问题污染长期指令。

## 流程

1. **确认授权**：只要求分析、总结或建议时不得改文件；明确要求更新、优化或沉淀时才实施修改。
2. **收集证据**：读取原始请求、预期与实际结果、错误或 diff、历次尝试、用户反馈，以及当时生效的 skills、`AGENTS.md` 和环境信息；证据不足就说明缺口。
3. **定位根因**：选择最小充分归属：
   - 当前实现错误：修复当前任务，不改长期规则。
   - 项目特有且稳定的约定：更新作用域最窄的 `AGENTS.md` 或既有项目文档。
   - 工具、网络、权限或外部服务偶发异常：记录条件和恢复方式，不改 skill。
   - skill 的触发、流程、知识或冲突缺陷：更新对应 skill。
4. **检查门槛**：仅当存在两个同类实例，或一个稳定复现、影响明确且规则缺口确定的实例，并且用户已授权时，才修改长期规则。
5. **最小修改**：写出“缺陷 X 导致决策 Y；改动 Z 应使条件 C 下产生 W”，然后叠加 `$skill-creator` 修改最窄所有者。
6. **回归验证**：运行结构校验，回放原失败案例，并用至少一个反例确认不会误触发；复杂或高影响改动再用不泄漏预期答案的新鲜上下文独立验证。

## 修改归属

- 触发不准：修改 frontmatter `description`。
- 步骤、顺序或停止条件缺失：修改 `SKILL.md` 正文。
- 重复且需要确定性的操作：使用 `scripts/` 并实际测试。
- 详细领域知识：放入 `references/`，正文只保留读取条件。
- 多个 skill 重复或冲突：按适用范围保留唯一、最窄的规则所有者。

## 开发 Skill 协同

| Skill | 唯一所有权 |
| --- | --- |
| `development` | 统一开发流程，以及前端、后端和语言领域 reference 路由 |
| `development-plan` | 复杂任务拆分、依赖、进度和交付安全计划 |
| `resolve-issue` | Issue 证据、实现入口和交付编排 |
| `merge-pr` | PR/MR 评审、冲突、远端合并和关联分支 |
| `commit` | 本地提交与已确认 AI 现场的收口 |
| `aliyun-deploy` | 阿里云生产部署、排障和回滚 |
| `skill-retrospective` | 重复失败归因与整套 Skill 的最小演进 |

- 规则只写在最窄所有者；调用方只声明何时调用、传递什么状态、复用什么结果，不复制被调用方流程。
- Skill 串联不能扩大用户授权；实现、提交、远端合并、生产部署分别判断权限。
- 修改调用关系时检查正向路径、相邻 Skill 反例、停止边界和最终状态，避免局部优化破坏完整交付。

## 护栏

- 不把项目事实写进通用 skill，不把个人偏好包装成普遍规律。
- 不因单次失败新增绝对禁令，不用堆叠规则掩盖根因。
- 修改前读取目标文件及相关规则，保留用户已有改动。
- skill 触发语义变化时同步 `agents/openai.yaml`；不创建 README、变更日志或复盘档案。

## 输出

简洁报告问题、证据、根因、修改决策、目标文件、验证结果和剩余风险。不要承诺“以后不会再犯”，只说明已覆盖的失败路径。
